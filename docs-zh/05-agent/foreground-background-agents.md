# 前台 Agent 与后台 Agent

实时语音模式使用两个相互协作的 Agent：

- 实时语音模型是前台 Agent。它负责实时对话，不能等待设备操作或长时间运行的工作。
- 旧版 Agent 循环是后台 Agent。它使用现有的运行时工具、记忆和 Episode 记录，一次执行一个排队任务。

编排层位于 `internal/agenttask`。它负责任务数据、状态转换、排队、取消和终态通知，不依赖 `internal/agent`。守护进程提供一个窄接口的 runner 适配器，把 `Run(ctx, prompt)` 映射到旧版 `agent.Runtime`。

两个对话上下文分别持久化在配置的会话根目录下：`sessions/user` 保存实时前台对话，`sessions/backend` 保存旧版设备操作上下文。用户上下文还会持久化实时前台自身的工具调用和工具结果，以便在打开新的实时 websocket 会话时恢复。后台的工具轨迹仍隔离在 `sessions/backend` 中；只有聚合后的任务更新会作为用户消息注入前台。为了控制实时上下文的大小，新的 websocket 会话只重放最近 10 个用户轮次，包括属于这些轮次的助手/工具消息。完整的用户历史仍保存在磁盘上。

实时模型拿不到逐轮状态，因此会话通过三种方式告诉它时间。发送给 provider 的指令末尾带有会话打开的时间；存储的系统消息保留稳定的指令，因此不会在每个会话中被重写。重放以一条状态消息结尾，给出最后一条被恢复消息的时间、当前时间以及两者之间经过的时间。这条消息还会在每个任务当前的目标下，报告被恢复轮次所创建的每个任务的后续情况，因为这些轮次只显示任务已被接受：它可能仍在运行，可能正在停止或已在某个页面上被停止，也可能因为设备重启而消失，因为任务只保存在内存中。消失的任务如果在被恢复的轮次中有结果，就算作已完成，否则算作丢失。被恢复的工作更新会标记为 `<notice>`，以免被当作用户说的话。

如果最后一条消息已超过 30 分钟，之前的轮次不会作为实时轮次重放，而是作为一份 `<earlier_conversation>` 记录发送，标记为已结束、仅供参考，后面跟着状态消息。这份记录完整保留用户和助手的文本，以及来自工作更新和任务查询的每个任务结果；工具调用不会被恢复。重放的轮次对模型的引导作用比指令更强，否则旧的话题、回答或工作更新会延续到数小时后才恢复的对话中。之所以保留这份记录而不是丢弃，是因为 `recall_session_chunks` 只搜索已压缩的分块，无法返回这些最近的轮次。

后台还通过 `schedule` 工具提供 [定时任务和例行任务](./schedules-and-routines.md)。MCU 定时器到期时，会在发起该任务的后台对话中恢复定时工作，并跟随压缩修订。定时运行和普通的排队后台任务都会等待运行时进入空闲状态。

前台实时会话可以由物理 GPIO 唤醒信号激活，也可以由发往 `/api/chat` 的文本请求激活。在没有连接实时会话时提交的文本请求，会在守护进程建立连接期间保持排队，然后成为该会话中的第一条用户消息。GPIO 初始化失败不会禁用 `/api/chat` 激活，因此在 PC 和其他没有开发板 GPIO 的主机上，同一条前台路径仍然可用。

一个未完成的前台响应有 60 秒的无进展超时。已接受的助手文本/音频以及前台工具调用/结果会续期该截止时间；麦克风流量、输入转写的修正、用量报告和过期的响应事件则不会。前台工具保留各自独立的 30 秒执行超时。没有待处理轮次的空闲对话不会超时。超时会让待处理的文本请求失败，并关闭实时会话，包括其播放和前台工具上下文。显式取消在可用时使用提供商的 ResponseInterrupter，停止播放和前台工具，并在收到终态确认之前保留准入所有权。迟到的输出不能续期取消截止时间。不支持中断、写入失败或缺少确认都会关闭会话；下一个请求随后会重新连接并恢复历史。成功的取消会让受支持的提供商会话保持连接。后台任务有自己的生命周期，取消前台响应不会取消它们。

Gemini 通过 `turnComplete=false` 的 clientContent 进行中断，让服务器等待输入，而不是请求另一次回答。这遵循 Google 的 ClientContent 中断语义，且无需关闭自动 VAD（手动 activityStart 需要关闭该开关）。Gemini 的 interrupted 之后紧跟 turnComplete 会被规范化为已取消的终态响应；即使被中断的响应没有 ID，守护进程也会保留它的终态所有权，而不会消耗新用户的待处理输入。参见 [官方协议](https://github.com/googleapis/googleapis/blob/64aa30b277168edd20efee0c9ceb4ca01248931d/google/ai/generativelanguage/v1beta/generative_service.proto#L1589)。空内容的取消负载由本地 WebSocket 协议测试覆盖；它在已部署的 Gemini 服务上的行为仍需实测验证。Gemini 的工具调用取消仅作用于列出的调用 ID：它会取消这些前台调用并丢弃它们迟到的结果，同时保留其他并行调用和响应生命周期。

聊天准入日志包含传入和当前活跃的请求 ID、响应 ID、占用时长以及每一个准入守卫。响应完成、取消、超时和会话释放会分别记录，便于诊断忙碌报告。

## 前台工具

实时模型会收到下面这个精简的目录：

| 工具                    | 用途                                                                          |
| ----------------------- | -------------------------------------------------------------------------------- |
| `get_current_time`      | 返回控制器本地的日期、时间、时区和 UTC 偏移。                    |
| `recall_memory`         | 召回长期的用户偏好、事实、规则和操作流程。                 |
| `save_memory`           | 保存一条长期记忆，无需等待后台任务。                   |
| `forget_memory`         | 按 `recall_memory` 返回的 ID 删除一条已保存的记忆。                   |
| `recall_session_chunks` | 召回比重放窗口更早的压缩历史。                        |
| `audio_volume`          | 读取或设置实时播放音量。                                        |
| `create_agent_task`     | 把后台工作加入队列，并立即返回任务 ID。                     |
| `cancel_agent_task`     | 取消排队中的工作，或请求取消正在运行的工作。                      |
| `update_agent_task`     | 替换排队中或正在运行的工作的完整目标。                              |
| `query_agent_task`      | 读取某个任务的状态和结果；未提供 ID 时读取所有未完成的任务。 |
| `response_user_action`  | 在用户完成所请求的设备操作后恢复后台任务。   |
| `end_conversation`      | 在告别语播放完毕后回到待机状态。                           |

`create_agent_task` 只负责把工作加入队列。前台响应从不等待后台 Agent 开始或结束。在结果更新或 `query_agent_task` 报告工作的结果之前，前台只会说它正在处理，而绝不会说已经完成。失败或已取消的结果会如实报告，并附上结果中列出的已完成步骤。工具描述和默认指令都明确说明了这一点。前台用自己的工具完成的工作（例如保存一条记忆）则直接报告。

当用户修改已在进行中的工作时，前台会使用任务 ID 和完整的替换目标调用 `update_agent_task`，而不是取消旧任务再创建新任务。不相关的新请求不属于修改：即使有其他工作正在运行，它也会通过 `create_agent_task` 获得自己的任务，因为把它并入正在运行的工作会打断那项工作。排队中的工作在开始时读取替换后的目标。正在运行的工作会以上下文内引导（steer）的形式收到替换目标：当前的模型调用或工具调用会被中断，更新后的目标作为一条用户消息加入后台对话，Agent 循环以相同的任务 ID 和后台上下文继续执行。

`create_agent_task` 总是启动新的工作；代码不会检查重复。前台根据自己的对话判断某个请求是否在重复仍在进行的工作，然后告诉用户工作正在进行，或者用 `query_agent_task` 查看，而不是再创建一次。不带任务 ID 时，`query_agent_task` 返回仍在执行中的任务，以及结果尚未交付给前台的已完成任务。重试已经完成或失败的工作会创建新的工作。未能识别出重复请求会导致工作执行两次；但新请求永远不会被搁置或丢弃。

记忆工具复用与后台 Agent 相同的注册项和存储，因此两个 Agent 读写的是同一个记忆平面。它们在前台的描述会按前台目录进行裁剪：后台 `recall_memory` 的描述会引导使用 `shell` 读取原始通知记录，而实时模型无法调用该工具。

之所以有 `recall_session_chunks`，是因为新的 websocket 会话只重放最近 10 个用户轮次。更早的轮次仍保存在磁盘上，但在被召回之前前台看不到。

## 结束对话

`end_conversation` 让会话回到待机状态。它不会引入新的状态：`runRealtimeSession` 返回，外层循环等待下一次 GPIO 唤醒或 `/api/chat` 激活，这与任何其他会话结束后的行为完全相同。

拆除是延迟执行而非立即执行的，因为如果工具一返回就取消会话，告别语会在说到一半时被截断：

1. 工具结果只记录请求；会话循环负责拆除。
2. 在告别语对应的 `response.done` 到达时，播放被收尾，并开始排空（drain），上限为 30 秒超时。
3. 排空报告扬声器已清空后，进入待机。

如果用户先重新开口，请求就会被放弃，无论是通过 `input_audio_buffer.speech_started` 还是通过聊天桥接发来的文本请求。两者都会让会话保持打开并回应新的输入。在告别响应仍处于活跃状态时到达的文本请求，会排队到该响应的 `response.done`；在播放排空期间到达的则会立即开始。在请求挂起期间，任务更新和语音通知不会被注入，因此排队中的结果不会在道别时启动新的响应。

待机不影响后台工作。在前台处于待机时到达终态的后台任务会自行激活前台，因此结果会被报告，而无需用户先开口。现有的会话拆除流程会把未交付的任务更新和待处理的用户操作交还给管理器；它们由下一个会话交付，无论这个会话是由任务更新还是由用户启动的。每个终态批次只尝试激活一次：如果该会话无法交付更新，更新会被放回队列，等待下一次激活，而不是循环地重复激活。待处理的用户操作本身不会激活前台；它会由下一个会话播报。

## 任务生命周期

任务使用以下状态：

```text
created -> queued -> running -> completed
                            -> failed
                            -> cancelling -> cancelled
                            -> running (waiting for user action)
                 -> cancelled
```

取消排队中的任务是立即生效的。取消正在运行的任务时，会先发布 `cancelling`；在旧版运行时因上下文取消而返回后，状态变为 `cancelled`。取消无法撤销副作用，因此被取消的运行会把已经成功的工具调用作为结果报告（工具、输入和输出，最近 20 条）。前台会收到带有 `cancelled` 状态的这份结果，并可以告诉用户哪些操作已经发生。

任务更新遵循以下状态规则：

- `created` 或 `queued`：在执行前替换已保存的目标。
- `running`：替换已保存的目标，并向当前活跃的后台运行发布一个“最新者胜出”的引导。
- 正在等待用户操作的 `running`：使旧的操作请求失效，并以替换后的目标恢复任务。
- `cancelling` 或终态：拒绝更新。

每个目标都有一个修订号。把引导持久化到后台上下文会推进已应用的修订号。如果后台运行在更新到达之后、但在持久化该更新之前返回，管理器会丢弃这个过期的结果，并立即用最新的完整目标再运行一次。这样就消除了直接给出最终答案与更新在 Agent 循环最后一次引导检查之后才到达之间的竞态。

## 队列顺序与 Web UI

等待中的任务按队列顺序一次运行一个。在用户操作之后恢复的任务，或在等待期间收到目标更新的任务，会加入队列末尾。队列最多容纳 64 个等待中的任务；队列已满时 `create_agent_task` 会报告错误。

Web UI 检查器会列出未完成的后台任务，并可以通过以下端点取消、重新排序和查看它们：

| 方法和路径 | 用途 |
| --- | --- |
| `GET /api/agent-tasks` | `{"enabled": bool, "tasks": [...]}`：未完成的任务，先列出已开始的工作，再按运行顺序列出等待中的工作。不在 Realtime 模式下或后台 Agent 关闭时，`enabled` 为 false。 |
| `GET /api/agent-tasks/{id}` | 单个任务的 `{"task": ..., "timeline": {"steps": [...], "omitted": n}}`。 |
| `DELETE /api/agent-tasks/{id}` | 取消该任务，规则与 `cancel_agent_task` 相同。 |
| `PUT /api/agent-tasks/order` | `{"task_ids": [...]}` 设置排队任务的顺序。列表必须恰好包含当前排队的任务；否则请求返回 `409`，且不做任何更改。 |

时间线是观察者视图，而不是后台上下文。它为每个任务保留最近的 40 个步骤：状态变化、工具调用（收到结果后原地更新）和助手消息，每条详情截断为 400 个字符。读取手机隐私数据的工具（剪贴板、日历、联系人、通知）的输出会被省略。时间线保存在内存中，覆盖未完成的任务和最近完成的 16 个任务，守护进程重启后会丢失。

## 后台中断上下文

当一次运行提前停止时，后台执行会写入持久化的 `notice` 消息，使下一次模型请求能够区分被中断的工作和已完成的工作。这些通知属于 `sessions/backend`；前端播放和任务结果交付保留各自的生命周期。

| 情形 | 通知和行为 |
| --- | --- |
| 取消正在运行的任务、取消旧版聊天请求、STT 唤醒取消或服务关闭 | `Interrupt [canceled]`；完成情况未确认。 |
| 另一个 `Runtime.Run` 接管 | `Interrupt [preempted]`。创建排队的后台任务不会抢占它的前一个任务。 |
| 执行截止时间到期 | `Interrupt [deadline_exceeded]`。 |
| 更新正在运行的任务或提交聊天引导 | 紧接在替换的用户指令之前写入 `Interrupt [steer]`；同一次运行继续。 |
| 模型/工具调用被中断，但其引导被撤回或未产生文本 | `Interrupt [steer_resumed]`；从最后确认的状态继续原任务。 |
| 未恢复的模型请求失败 | `Interrupt [model_error]`。 |
| 模型在给出回复或工具调用之前达到输出 token 上限（通常发生在推理过程中） | `Interrupt [output_truncated]`。空的模型轮次不会被保存，因此下一次请求可以继续对话。 |
| 上下文预算、压缩或其他执行失败 | `Interrupt [execution_error]`。既没有回复也没有工具调用的模型轮次不会保存到历史中。 |
| 用尽迭代或耗时预算，或连续解析失败 | 带有停止原因的 `Interrupt`。 |
| 重复操作或工具结果停滞 | 循环防护添加提示，运行继续。 |
| 设备触控模式不兼容 | `Interrupt [device_mode_mismatch]`。 |
| 运行时 panic | 在仍能持久化时写入 `Interrupt [panic]`；panic 会被重新抛出。 |
| 进程意外退出且没有记录结束 | `Interrupt [agent_restart]`，在下一次后台输入之前恢复；完成情况未知。 |
| `request_user_action` 或 `wait_for_wakeup` 成功 | `Pause [...]`；有意的暂停不等于任务完成。 |

运行时在执行前会以原子方式在 `sessions/backend` 中记录 `.pending-run.json`。正常结束或持久化中断之后，它会清除该记录。通知写入失败会留下恢复记录；如果恢复也失败，下一次运行会报告错误，而不是在缺少该上下文的情况下执行。恢复会沿着当前的压缩谱系进行，对通知去重，并保留历史轮换/清空的效果。

通知追加在工具结果之后，保持工具调用/结果的配对关系。它们提示模型在重复某个操作之前先验证当前的设备状态，因为取消无法撤销副作用。忽略取消的工具必须先返回，循环才能记录其结果并结束。

正常回答、已恢复的模型错误、单个可恢复的工具错误、HTTP 客户端断开、前台实时中断，以及循环完成后停止 TTS，都不会产生后台中断通知。取消排队中的工作或已暂停的任务不会中断活跃的 AgentLoop；任务管理器会单独处理这些状态变化。

## 结果交付

已完成、失败和已取消的任务会作为用户消息交付给前台模型。交付遵循三条规则：

1. 一个终态更新会启动一个 500 毫秒的滑动防抖窗口。每多一个更新就重置该窗口，因此时间上相近完成的结果会合并到一条消息和一次前台响应中。
2. 只有在前台会话空闲时才注入更新。它绝不会打断用户正在说的话、活跃的响应，或通过实时聊天桥接转发的文本请求。
3. 在前台处于待机时产生的终态更新，只要仍处于待处理状态，就会激活前台会话。管理器为每个终态批次发布一个唤醒信号，与会话自己拥有的排空信号分开；守护进程会记录管理器终态序列的水位线，因此一个批次最多激活一个会话。

终态结果交付有三个由管理器掌控的阶段：排队、被某个前台会话认领，以及交付中。排空会认领更新，但不会把它标记为已交付。就在注入文本之前，前台会根据管理器的当前状态核对每一个已认领的快照；在实时提供商接受响应请求之后，再确认该更新。如果会话先结束，认领会被释放回待处理队列，留给之后的会话。

对已完成、失败或已取消的任务调用 `cancel_agent_task`，会保留该任务的历史状态，但在交付处于排队或已认领阶段时屏蔽其结果。因此，已在前台待处理列表中的已认领结果会在最终核对时被移除，永远不会被播报。一旦交付已经开始，提供商响应就是不可回退的节点，不会因任务取消而被追溯中断。

终态任务绝不会携带待处理的用户操作：任务到达终态时操作就会被清除，因此前台永远不会被要求为已完成的工作完成某个操作，拆除流程也能区分恢复的结果更新和恢复的操作请求。

## 用户操作转交

`request_user_action` 会感知当前模式：

- 在普通的旧版运行中，它保留现有的人工转交响应（`HUMAN_HANDOFF_REQUESTED`）。
- 在后台任务运行中，它会发布一个待处理操作，同时让任务保持在 `running`。后台 Agent 循环此时返回，但任务并未到达终态，其待处理操作仍可查询。

前台 Agent 在空闲时收到该请求，并告诉用户需要在设备上做什么，包括完成后要告诉它。用户确认完成后，前台使用任务 ID 和一条简洁的 `user_message` 调用 `response_user_action`。管理器清除待处理操作，并在同一个后台运行时/会话上启动新的循环。`user_message` 作为下一条用户消息追加到现有上下文中，以便后台 Agent 验证新状态并继续原任务。如果实时会话在交付之前结束，待处理操作会保留给下一个前台会话。

在任务等待用户操作时更新任务，与响应该操作不同：旧请求不再具有权威性，因此管理器会清除它，使任何已认领的前台快照失效，并以完整的替换目标恢复后台。
