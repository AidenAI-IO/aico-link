# 记忆平面

本文介绍 Aico 当前基于文件系统的记忆架构。会话记忆另见 [会话记忆压缩](session-memory.md)。

## 职责

记忆平面将持久化状态分为四类：

- 会话记忆保存当前对话和压缩后的历史；
- 长期记忆保存用户明确要求保存的信息，以及用户陈述的关于自身的持久事实；
- 设备记忆保存可复用的设备、应用、导航、操作流程、校准、失败和事实知识；
- 任务 Episode 保存不可变的执行证据，用于审计和后台整合。

自动 Episode 学习只写入设备记忆（Device Memory），不会在长期记忆中创建用户画像、偏好或规则条目。

## 记忆准入策略

有三个写入方会持久化记忆，它们对哪些内容可以保留都遵循同一套规则。模型提出记忆，代码负责执行那些不依赖于理解用户所用语言的规则。

| 写入方 | 触发方式 | 写入位置 |
| --- | --- | --- |
| `save_memory` | Agent 在对话中调用 | 长期记忆 |
| Notification Memory | 共享空闲窗口 | 临时记忆或长期记忆 |
| Episode Memory | 共享空闲窗口，在设备任务之后 | 设备记忆 |

| 信息 | 规则 |
| --- | --- |
| 明确要求记住的内容，或面向未来的偏好、称呼方式或规则 | 保存 |
| 用户陈述的关于自身的持久事实，例如所在城市、职业、角色、常用工具或背景 | 无需明确的“记住”请求即可保存；不会从引述、第三人称陈述或临时任务中推断 |
| 要求在之后某个时间执行操作或提醒 | 交给 `schedule` 工具处理，参见 [定时任务与例行任务](schedules-and-routines.md)。不作为记忆保存 |
| 用户提到但未要求提醒的近期计划 | 不保存到长期记忆。对话会保留它们，上下文压缩也会保留它们，参见 [近期计划](#近期计划) |
| 来自通知的有时效的事实，例如账单和快递 | 带过期时间的临时记忆；仅限 Notification Memory |
| 凭据和支付卡号 | 默认不保存，参见 [敏感记忆](#敏感记忆) |
| 公共信息、闲聊、营销内容，以及用户说过不要保留的任何内容 | 从不保存 |
| 设备经验 | 仅限 Episode Memory，并须遵守下文的证据规则 |

### 近期计划

像“我明天上午要体检”这样的计划只在几天内有用，不属于用户的长期画像，所以 `save_memory` 不会保存它。该工具要求一个遵循上面准入表的 `durable` 参数：一次性的计划、预约、提醒或临时状态为 `false`；持久的偏好、规则、操作流程或个人事实为 `true`，包括用户限定在某段时间内的偏好。不存在固定的时间阈值。`durable=false` 的调用会返回 `status=refused` 且不写入任何内容，无论是新增记忆还是通过 `replaces_id` 替换记忆；Agent 随后回复时不会声称已经记下或保存了该计划。`durable` 是调用模型自己的分类，是保存前的自检，而不是独立的准入检查：误判计划的模型同样可能报告 `durable=true`。省略 `durable` 的调用不会被拒绝，因此忽略 schema 的模型仍会像以前一样保存。计划会留在对话中。上下文压缩总结较早的消息时，摘要中有一个专门记录用户计划和有时效信息的部分：压缩器会用配置时区下的发送时间标注每条消息，并要求模型把相对日期解析为绝对日期，这样“明天”在说出的那天之后依然正确。只有用户给出了具体时刻时才会保留时刻。清除对话历史会将这些计划连同其余对话一起删除。

### 敏感记忆

`save_memory` 接受一个 `sensitive` 参数：密码、PIN 或类似机密为 `credential`，卡号为 `payment_card`。由模型声明类型，是因为没有任何关键词列表或数字模式能在用户可能使用的每种语言中可靠地识别机密；例如，卡号校验和同样会接受十分之一的订单号或快递单号。

只有当模型同时将 `user_request` 设置为用户本人要求记住它的原话时，敏感记忆才会被保存。代码会检查这些原话是否出现在本次运行的用户输入或 steer 消息中，或出现在本次运行之前用户的两条消息中，比较时只看字母和数字且不区分大小写。之前的消息用于覆盖在机密出现前一轮提出的请求，例如先说“记住我的门禁密码”，在 Agent 询问后再给出密码。上下文压缩摘要虽然以用户消息的形式存储，但由模型写成，因此永远不算作其中之一，检查窗口也不会越过它延伸到更早的消息。引述必须至少包含两个字母，因此只引用机密值本身不算数。引述检查可以防止模型捏造请求，但像“我的 Wi-Fi 密码是……”这样的陈述同样是用户的原话。因此，另一次独立的模型调用——请求判定器——会读取相同的用户消息、候选记忆以及模型引用的请求，并回答用户是否要求记住这条信息。陈述机密不算请求，要求记住其他内容也不算，之后的撤回会取消请求。判定器使用主模型，超时为 20 秒。如果引述检查失败、判定器认为用户没有提出请求，或判定器调用失败或超时，工具都会返回 `status=refused`，不写入任何内容，Agent 会告诉用户没有记住。用户可以再次提出请求，而误写入的机密则会一直留存。

模型也可能在机密上不设置 `sensitive`。当未声明的记忆中包含一段至少四个 ASCII 字母和数字、且其中含有数字的连续字符（大多数密码、PIN 和卡号的形态）时，工具会询问同一个判定器该内容是否为机密。用户没有要求保留的机密会被拒绝；用户要求保留的机密会被保存为敏感的 `credential`。不具备这种形态的内容，以及判定器调用失败时的所有保存，都会照常保存，因此该检查只在可能存在机密时才增加一次模型调用，且绝不会阻止普通记忆。不含数字的机密，例如模型没有标记为敏感的纯字母密码，不会被判定，而是作为普通记忆保存。每次判定都会记录其结论和延迟。

已保存的敏感记忆会在其文件和索引条目中标记为 `sensitive: true`。只有当查询的 tags 或 entities 与之匹配时，`recall_memory` 才会返回它，按类型浏览时永远不会返回。它不会出现在用户画像中，也不会出现在展示给 Notification Memory 的相关记忆中。和其他所有记忆一样，它仍然是一个普通文件。

由于敏感记忆在被召回之前从不出现在模型的上下文中，当用户询问已保存的机密时，模型可能出于自身的谨慎而断定该机密从未被保存。因此默认行为提示词要求：在 Agent 表示不知道、没有保存或无法提供用户要求回忆的内容之前，必须先针对该问题的主题执行一次 `recall_memory` 查询；用户画像部分也会说明其列表并不完整。Agent 会给出用户要求的机密；其他仅仅与查询匹配的机密最多只提及名称，绝不提供值。

通知永远不构成明确的记忆请求，Notification Memory 的提示词也会要求模型忽略 OTP 和机密。

### 系统提示词中的用户画像

系统提示词的末尾是一个“User profile”部分，按优先级从高到低列出当前有效的 `profile`、`preference` 和 `rule` 记忆，总长度约 1,500 个字符以内。放不下的条目会被跳过，因此其后较短的条目仍会被列出。这些条目从记录中读取，而不是从模型编写的 `profile.md` 中读取，因此该部分与实际保存的内容一致。这样 Agent 无需调用 `recall_memory` 就能应用已保存的偏好。

一个会话会一直保留其系统提示词，直到历史被清除或配置发生变化，这可能长达数天。每次运行之前，运行时都会根据记录重建该部分。如果它与会话中的版本不同，例如因为用户保存、修改或遗忘了一条画像记忆，系统消息就会在新的会话修订版本中被重写，这与上下文压缩使用的机制相同：对话继续进行，旧的对话记录保留在磁盘上，定时任务继续沿用该谱系。画像未变化时，会话和提供商的提示词缓存都不会受到影响。画像部分不属于决定是否恢复已保存会话的配置，因此画像变化永远不会开启新的对话。如果无法读取画像或无法重写会话，本次运行会记录一条警告，并继续使用会话中已有的该部分。

在实时模式下，前台语音模型的指令末尾也带有同样的部分。它在每个提供商会话打开时读取，因此对话中保存的画像会从下一个会话开始生效。已保存的实时用户上下文会记录该会话打开时使用的版本。如果无法读取画像，会话会记录一条警告，并保留已保存用户上下文中已有的该部分。

敏感记忆、`fact` 记忆以及内容由 Notification Memory 写入的记忆不会被列出；通知内容由第三方编写，不能成为指令。每条记录的 `origin`（`user` 或 `notification`）标明了当前内容的作者。仅强化用户记忆的通知只增加证据，不改变其 origin；重写内容的通知则会接管 origin。在 `origin` 字段出现之前保存的记录，如果带有通知来源，则被视为由通知写入。

## 运行流程

设备记忆不会被注入到每个提示词中。当任务实质上依赖已保存的设备或 UI 知识时，由模型在执行过程中决定是否调用 `recall_device_memory`。运行时不会在运行前进行相关性路由，也不会强制第一次工具调用。

```text
Run starts
  |
  v
build the normal model-controlled run
  |
  v
Agent calls recall_device_memory only when needed
  |
  v
Agent executes tools and records an Episode
  |
  v
persist the completed Episode
  |
  +--> update deterministic device/app profiles
  |
  `--> notify the shared background MemoryWorker
```

召回工具会记录实际展示给 Agent 的 ID。后台 Worker 在判断一条新经验是否应更新现有记忆时，会优先检查这些记录。

## 存储布局

记忆存储在 `<config_dir>/memory/` 下。

```text
memory/
├── session/                     # active conversation memory
├── session_archive/             # closed session logs
├── long_term/                   # explicit user memory
├── episodes/                    # immutable task Episodes
├── device/
│   ├── profile.yaml             # deterministic device profile
│   ├── apps/                    # deterministic app profiles
│   ├── procedures/
│   ├── navigation/
│   ├── calibration/
│   ├── failures/
│   └── memories/                # facts and uncategorized Device Memory
└── lifecycle/
    ├── reflection.yaml          # Episode Memory processing ledger
    └── reflection.lock          # cross-runtime batch lock
```

保留 `reflection.yaml` 和 `reflection.lock` 这两个名称是为了升级兼容。它们现在归 Episode Memory 流水线所有，而不是已被移除的、仅处理失败的 Reflection 实现。

## 用户记忆召回

`recall_memory` 会同时搜索临时记录和长期记录。`tags` 和 `entities` 中的主题词可以匹配任一元数据字段，因此保存和召回时对某个词的分类不同，并不会导致记录无法访问。在所请求字段中的匹配比在另一个字段中的匹配权重更高；标题、摘要和内容的匹配也会计入相关性。合并两个 Store 的结果时使用相同的相关性评分。有效状态和过期检查依然适用，仅类型匹配不能让一条无关记录满足主题查询。

对于主题查询，相关性相同时临时记录排在长期记录之前。仅带 `types` 或不带任何词的浏览会对所有记录同等匹配，因此长期记录排在前面，并且在有长期记录可用时，临时记录最多只占限额的一半。这样，积压的通知结论就无法把用户保存的偏好挤出结果。

对于要求为将来的对话记住信息或规则的明确请求，Agent 必须在 `save_memory` 调用成功后才能确认已持久化。纠正已有的长期记忆时，Agent 会先召回它，并将其 `id` 和 `revision` 作为 `replaces_id` 和 `expected_revision` 传给 `save_memory`。Store 会拒绝过期的 revision 或不同的记忆类型；它不会仅凭 tags 或 entities 匹配来选择要替换的记录。

`recall_session_chunks` 搜索后端 ContextManager 的共享分块索引。主题查询会匹配 tags、entities 和摘要文本，包括配置的提取词表之外的主题。显式的分块 ID 仍是精确选择器。结果保持从新到旧的顺序和所请求的数量上限。主题结果为空时，允许再进行一次更宽泛的查询，然后才报告对话历史不可用。

## 设备记忆召回

正常的 `recall_device_memory` 结果有以下限制：

- 只返回 `active` 记录；
- 最多返回五条记录；
- 输出限制在约 4,800 个字符以内；
- 排除已过期或不适用于当前设备的记录；
- `pending`、`disputed` 和旧版 `conflicted` 记录仅作为整合时的上下文。

召回工具使用模型提供的查询，搜索有效且适用的设备记忆。它会在 Episode 上记录实际返回的 ID；运行时不会注入候选列表，也不会用它来改写模型的查询。

如果一个组合了 tags 与搜索词或 entities 的查询没有匹配结果，工具会将 tags 作为排序词重试。entity、type 和设备过滤条件仍然有效。提供了主题词或 tags 时，至少要有一个与记忆匹配；仅 entity 匹配不能确立主题相关性。只包含 tags 的查询保持精确的 tag 过滤。操作流程（Procedure）返回时会完整保留所有已存储的步骤，放不进召回预算时则整体省略。

## Episode 记录

每次带有用户目标的已完成运行，都会在后台学习开始之前持久化一个任务 Episode。成功、失败和中断是记录状态，而不是学习的准入规则。

一个 Episode 可以包含：

- 原始用户目标和规范化后的范围；
- 工具调用、输入、结果和结构化错误；
- 用户的 steer 或纠正事件；
- 截图和操作后截图的引用；
- 被召回的记忆 ID；
- 记录的运行时结果和最终回答。

截图二进制数据作为 Episode 附件（artifact）存储。事件记录中包含的是相对引用，而不是嵌入大段 base64 数据。

记录的 `outcome.success` 值不被视为经过验证的事实，而是作为之后评估的输入证据。

Episode 索引列出每个 Episode，并附带简短的用户目标和摘要（各自上限 300 个字符），用于查找；完整的目标和轨迹保存在该 Episode 自己的 `episode.yaml` 和 `events.jsonl` 中。索引包含两个文件：

- `memory/episodes/index.yaml` 是快照。
- `memory/episodes/index-log.jsonl` 是只追加的日志，记录自快照以来写入的条目。后面的行会替换前面具有相同 id 的行。

开始和结束一次运行只会向日志追加一行，从不重写快照，因此单次运行的开销不会随已存储 Episode 的数量增长。日志会在 Agent 启动时折叠回快照；当日志达到 256 KiB 或删除 Episode 时，`episode_retention` 清理器也会执行折叠。快照会记录它所吸收的日志的 id，因此被中断的折叠遗留下来的日志不会被重放。每个进程都在内存中保存合并后的索引，并在自己追加时更新它。

### Episode 存储保留策略

存储监视器的 `episode_retention` 清理器随例行维护检查运行（在每个存储等级下都会运行）。它会删除整个 Episode 目录及其索引条目：

- 结束超过 30 天的 Episode。
- 索引中最新 1,000 个之外的最旧 Episode。
- 不在索引中、且最后修改时间超过 30 天的 Episode 目录。

它从不删除正在运行的 Episode，也不删除被有效的长期记忆或设备记忆引用为证据的 Episode（`episode` 来源或证据引用）。Episode Memory 会在运行结束后几分钟内把后续运行所需的内容提炼进设备记忆，因此较旧的 Episode 仅作为执行证据。清理器与所有 Episode 写入方获取相同的按目录锁。

整合台账单独设有上限。它保留最近 64 个 `done` 或 `ignored` 终态，同时保留处理中和重试状态。设备记忆的 TTL 同样只影响召回：过期记录会被排除在搜索之外，但 StorageMonitor 不会例行删除它们的 YAML 文件。

## Episode 记忆整合

后台流水线如下：

```text
completed Episode batch (up to three)
  |
  v
deterministic prefilter
  |
  v
one background LLM assessment and extraction for the batch
  |
  v
code-level evidence and type validation
  |
  v
create or update Device Memory
```

### 准入

当 Episode 包含以下任一内容时，才有资格进行模型调用：

- 成对的设备工具调用和结果；或
- 非取消的结构化错误。

问候、普通对话、仅涉及记忆的轨迹、成功的纯 Web 轨迹，以及在有意义的设备操作之前就取消的情况，都会被直接忽略，不调用模型。

被中断的 Episode 如果在中断前包含有用的设备证据，仍然具备资格。

### 模型输入

模型接收的是 Episode 的有界视图：

- 最多最近 60 个事件；
- 工具输入、结果、错误和用户纠正；
- 最多三张已持久化的截图；
- 在约 12,000 个字符的预算内，最多八条相关的设备记忆。

相关记忆的选择优先级依次为：Episode 期间被召回的记录、相同范围内的有效记录、相同范围内的 disputed 记录，然后是其他文本匹配。

`verifier_decision`、`ObservedState` 和 `VerifierReason` 等 PEV 字段不参与此流水线。

### Episode 评估

模型会独立给出：

```text
goal_result = achieved | not_achieved | unknown
```

`achieved` 和 `not_achieved` 必须引用 Episode 中的直接事件，例如工具结果、截图、结构化错误或用户纠正。缺少最终证据时，结果必须为 `unknown`。

因此，一个记录为成功的结果可能被评为 `not_achieved`。这会纠正所学到的记忆，但不会追溯修改前台 Run 的结果。

### 候选类型

一个 Episode 可以产生零到三个相互独立的候选。

| 类型 | 用途 | 最低证据形态 |
| --- | --- | --- |
| `procedure` | 可复用的多步路径 | 多次设备调用和结果，外加一次观察 |
| `navigation` | 可复用的页面入口或跳转 | 操作、结果以及操作前后的观察 |
| `calibration` | 坐标或屏幕关系 | 坐标输入和操作后的证据 |
| `failure` | 防护条件、停止条件或恢复方法 | 直接的问题证据或未达成证据 |
| `fact` | 稳定的设备、应用或页面观察 | 观察到的工具结果 |

Episode 级别的失败不会自动产生失败记忆（Failure Memory）。Failure 候选必须包含对将来任务可复用的指导。

工具观察是设备、应用或页面知识的证据。观察来自工具结果这一事实，并不是丢弃它的理由。要保留，必须是超出常识和 Agent 已收到的建议之外、可执行且有明确范围的信息。重复重试说明，或在通用建议中加上应用名称，都不满足这一要求。如果一个观察到的约束或变通方法，其有证据支持的条件会改变将来任务的执行方式，它就符合条件。仅凭观察并不能确立持久性，也不能让某次运行特有的值变得可复用。

提取、遗漏审查和保留审计通过 `episodeMemoryBuiltInGuidanceRule` 共享这一策略。遗漏审查还会接收一次完整的提议 schema 和类型规则。操作流程的指导和候选证据必须描述同一条有证据支持的路径；更短的路径需要有自己的证据。对于保留下来的 Failure 候选，保留审计必须说明超出工具自身建议的 `incremental_knowledge`，并引用 Episode 中属于观察事件的 `knowledge_evidence_refs`。缺少任一项的保留 Failure 审查会被代码丢弃，被引用的引用则保留在留存的证据中。建议的恢复方法并不能证明其有效，但观察到的设备特定约束仍可作为设置防护条件的理由。这些语义判断仍是模型的判断，而不是结构化证据校验器提供的保证。

当 `goal_result=not_achieved` 时，候选不能声称整个目标路径已成功。只有在范围中明确标注为部分（partial）时，才允许保留一个已在局部得到证明的 Procedure。

Procedure 通过 `step_refs` 选择其可执行路径：按顺序排列的工具结果事件 ID，每个都与一次设备调用配对，并包含在 `evidence_refs` 中。更宽泛的证据可以包括解释变通方法的失败尝试；只有被选中的步骤才会成为可执行动作。缺失、重复、乱序、未配对、未被引用或明确失败的步骤结果都会被拒绝。非错误的观察是否证明了成功、所选路径是否完整，仍由模型和保留审计判断。已存储的记忆不会被重写；没有显式路径的 pending 操作流程候选不会被准入。

评估夹具使用 `consolidation_expectation.required_procedure_steps` 描述完整的返回序列：每一步一个描述子串，按顺序排列，不允许有多余的步骤。匹配的文字描述或子序列无法掩盖插入在有效路径之前或之中的失败操作。

## 创建、更新与冲突

模型提出 `create` 或 `update`，但准入、存储路径和最终状态由代码决定。Processor 提供用于该决策的有界相关记忆视图，并分配一个确定性的创建 ID。Store 执行显式的创建意图，不会再进行第二次相似度或范围判断。

如果一个创建提议遗漏了有界视图之外的已有记录，重复问题会作为之后一次显式的整合/更新操作来处理，而不是在持久化时悄悄改写创建意图。

更新要求提供提取期间观察到的确切记忆 revision，并会保留之前的证据。Procedure 更新会用完整的 `step_refs` 路径替换可执行步骤；旧步骤保留在有界的修订历史中，而不是追加到当前路径上。其他设备记忆的更新仍会合并步骤。主体内容发生实质变化时，会把先前的值追加到有界的修订历史中。

如果可以通过添加版本、页面、账号状态或其他前置条件来调和证据，记忆就会以带条件的规则形式保持有效。

如果同一范围内仍存在互不相容的结论，记忆会变为 `disputed`。disputed 记录会被排除在正常召回之外，但仍可供之后的整合使用。

## 幂等性与恢复

处理台账使用 `episode_id@extractor_version` 作为键，并使用以下状态：

```text
processing -> proposed -> done
                    `--> retry
processing/proposed -> ignored
```

提议会在写入设备记忆之前持久化，因此恢复时可以直接应用已有的提议，无需重复调用模型。

对于单个 Episode，正常结束的模型响应如果为空或是无效 JSON，会得到终态 `ignored` 结果。当包含多个 Episode 的批次在没有可重试原因的情况下失败时，无法看出是哪个 Episode 导致的，因此每个 Episode 会被单独重试，而不是随整个批次一起丢弃。这次拆分不计入任何 Episode 的尝试次数；之后的单独重试才计入。模型请求失败或超时会被重试，因为没有收到响应。被识别为输出 token 截断的响应会被安排重试；其中的 Episode 会被单独重试，以免 Worker 重放同一个过大的批次，并且提取、遗漏审查和保留审计调用在每次重试时都会获得更大的输出预算。失败日志会记录响应大小，但从不记录响应正文，因为其中可能重复包含敏感的 Episode 值。日志和处理台账会保留失败类别（请求失败、超时、无效 JSON、批次形状不匹配、截断、空响应或审查失败），并丢弃包装在其中的提供商文本。每次安排的重试都会记录其尝试序号。进程在进入 `processing` 之后、持久化提议之前崩溃的情况，会在其租约过期后被忽略。

如果目标记忆的 revision 在更新之前发生变化，过期的提议会被丢弃，Episode 会基于最新的 revision 重新提取。输出 token 截断以及保留/遗漏审查失败，也可能为同一个提取器版本安排另一次模型调用。

## 延迟隔离

Episode 整合不会在前台 Agent 循环中增加同步的 LLM 调用、截图、OCR 处理或验证器。

Worker：

- 在空闲延迟后启动；
- 每批最多处理三个 Episode；截断重试会把批次降为每次模型调用一个 Episode；每个 Processor 批次使用一次模型调用，并在本地应用返回的结果；
- 同一时间只有一个进行中的后台模型调用；
- 前台任务开始时取消该调用；
- 前台任务结束后恢复调度。

Episode 轨迹的持久化发生在安排后台维护之前。维护失败会被记录日志，不会替换面向用户的任务结果。

## 通知记忆

Notification Memory 扩展了记忆平面，同时保持 `ble_service` 作为事件生产者。Agent 通过 `ble_service` API 消费通知；记忆处理仍在 Agent 中进行。在共享空闲窗口内，Agent 侧的 `NotificationProcessor` 消费 BLE 事件环，`NotificationContext` 在记忆提取之前对经过清洗的来源记录进行去重和持久化。

存储布局中新增了两个根目录：

```text
memory/
├── notifications/              # sanitized source evidence and cursors
├── temporary/                  # time-bounded recallable conclusions
│   ├── index.yaml
│   └── memories/
└── long_term/                  # durable user memory
```

临时记忆使用长期记忆的记录和索引 schema，要求提供 `expires_at`，并通过现有的 `recall_memory` 工具搜索。对于同一主题，相关且未过期的临时记忆排在长期记忆基线之前，但不会替换它。

记忆平面拥有一个共享的 `MemoryWorker`，注册两个场景的 Processor，并在注册完成后才启动 Worker。Worker 是唯一的空闲调度器：Agent 空闲五分钟后，它按 Episode -> Notification 的顺序串行调用各 Processor，并在前台任务开始时取消进行中的工作。只要 Agent 保持空闲，有界的待处理批次会继续执行，无需再等五分钟。每个 Processor 各自负责自己的输入、批大小、提议校验、重试状态和 Store Apply 规则。Processor 的失败相互隔离：错误会被记录并重试，不会阻止之后注册的场景运行自己的批次。正常的待处理工作在当前空闲窗口内继续；失败的批次则等待空闲重试延迟，以避免热循环。

| Processor | 触发方式 | 批次 | 输出 |
| --- | --- | --- | --- |
| EpisodeProcessor | 共享的 Agent 空闲窗口 | 3 个 Episode / 1 次 LLM 调用 | 设备记忆 |
| NotificationProcessor | 共享的 Agent 空闲窗口 | 10 个事件 / 1 次 LLM 调用 | 临时记忆或长期记忆 |

通知持久化不会启动 30 秒计时器。一次 Notification Processor 运行会先消费 BLE 事件环，再检查其持久化的待处理游标；没有待处理工作时直接返回，不会再次轮询。

## 兼容性

旧版 `reflection:v1` 失败记忆仍然可读。省略了 status 的旧设备记忆文件保持原有含义，被视为 active。

旧的仅处理失败的 Reflection 处理器、同步的 Procedure/Navigation/Calibration 提取、自动生成的已验证任务路径长期记忆，以及基于结果的置信度更新，都已不再启用。

## 验证

核心回归测试套件覆盖预过滤、虚假成功、截图附加、按类型的证据校验、被中断的 Episode、去重、冲突隔离、revision 恢复、召回预算和前台抢占。

在 `src/agent` 下运行针对性检查：

```bash
go test ./internal/agent -count=1
go vet ./...
```

仍需要在真实设备上验证，以衡量真实模型提供商下的多模态评估质量和前台 p50/p95 延迟。
