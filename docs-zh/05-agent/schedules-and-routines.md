# 定时任务与例行任务

Agent 的 `schedule` 工具用于创建一次性任务和重复执行的例行任务。它使用 MCU 的单个唤醒倒计时，并通过现有的后台运行时恢复工作。它不会让 Agent 轮次保持打开，也不会用 shell sleep 来等待。

守护进程在所有输入模式下都会安装该工具。在带后台 Agent 的实时语音模式下，前台会像处理其他设备工作一样，通过 `create_agent_task` 委托定时请求。定时执行需要后台 Agent；在实时模式下禁用该 Agent 时，创建请求会被拒绝。

## 工具接口

创建任务前，先用 `action: "list"` 检查是否已有相关任务。该工具接受以下操作：

| 操作 | 字段 | 行为 |
| --- | --- | --- |
| `create` | `task`，`delay_s` 或 `run_at` 二选一，可选 `interval_s` | 在当前后台会话中保存一个任务。 |
| `list` | 无 | 返回定时任务、状态、最新结果/错误，以及 MCU 计时器错误（如有）。 |
| `update` | `id`，完整替换的 `task`，`delay_s` 或 `run_at` 二选一，可选 `interval_s` | 替换已停止或待执行的定时任务，保留其原始会话。 |
| `cancel` | `id` | 取消未来的执行；如果该任务正在运行，则请求取消。 |

`delay_s` 是 1 到 604800（七天）之间的整数。`run_at` 是带显式时区的绝对 RFC3339 时间戳。更远的截止时间会使用连续的 MCU 倒计时，每段不超过七天。对于一次性任务，`interval_s` 为 0 或省略；对于重复的例行任务，取值为 1–604800。间隔以经过的秒数计算；它们不是本地日历规则，也不会根据夏令时调整。

例如，十分钟后继续检查一个快递：

```json
{
  "action": "create",
  "task": "Check the shipment we discussed and report any delivery update.",
  "delay_s": 600
}
```

从指定时间开始，每 24 小时运行一次任务：

```json
{
  "action": "create",
  "task": "Check the order status and report any changes.",
  "run_at": "2026-10-23T09:00:00+02:00",
  "interval_s": 86400
}
```

现有的工具 HTTP 端点 `POST /api/tools/schedule` 也接受这些输入，使用与其他工具相同的请求封装。此时必须已存在一个后台会话。成功的修改操作会在 `result` 下返回例行任务；列表操作在 `result` 下返回数组。每个成功的工具响应都包含 `timer_error`。非空错误表示定时任务已保存，但 MCU 计时器的设置或对账尚未得到确认；此时不要告诉用户唤醒已就绪。守护进程运行期间会重试。如果 MCU 不可用，或有一个独立设置的计时器处于活动状态，初次创建会失败。

## 执行与会话连续性

定时任务会记录其来源后台会话的 `session_id`。到期时，其任务作为新输入追加到该对话中，保留现有的工具结果和对话上下文。运行时会等待当前活动的运行结束。普通的排队后台任务也会等待，因此它们不会抢占定时运行。交互式的用户请求仍然可以打断定时工作。

会话标识在 Agent 重启后依然保留，包括在之后某个日期重启。生成的提示词日期会以追加状态的方式刷新，而不会替换对话。上下文压缩会创建修订版本；定时执行会沿着这条谱系继续，而不是重新打开一份过时的对话记录。清除历史记录，或者某项配置变更用新的根替换了对话，会使旧的定时任务显式失败。它绝不会重建已清除的历史，也不会静默地在无关对话中执行。如需在新对话中继续，请在新对话中创建新的定时任务。

结果保留在后台对话记录和 `schedule(action="list")` 中。该调度器本身不会启动前台语音响应，也不会合成语音。定时任务可以像往常一样使用现有的执行工具。

## 持久化与恢复

状态以原子方式存储在 `<config_dir>/routines/state.json` 中，包括事件游标、待处理工作、定时任务/会话映射以及最新结果。常规配置目录为 `/userdata/agent`。状态文件权限为 `0600`，其中不存储任何模型凭据。

如果加载或恢复例行任务状态失败，守护进程会记录错误，并在没有 `schedule` 工具的情况下继续处理 HTTP 和语音请求。它会保留状态文件不动，以便检查和恢复。修复所报告的状态或存储问题后重启 Agent，即可重新启用定时功能。加载未变化的状态不会重写它；但持久化已恢复的中断工作仍需要可写的存储。

正常生命周期如下：

```text
scheduled -> queued -> running -> completed
                              -> scheduled (next repetition)
                              -> failed
scheduled / queued / running -> cancelled
running at shutdown/restart  -> interrupted
```

MCU 唤醒事件（`rtc_timer`，来源代码 4）使到期的工作变为可执行。ASR 和其他唤醒来源不会运行定时任务。游标推进和排队工作会在执行前一起持久化。启动时也会确认硬件计时器：一个先前已设置、现已到期的倒计时可以恢复丢失的事件。当 MCU 状态不可用时，仅凭主机时钟绝不会派发任务。

多个定时任务共享最早的倒计时。对账时会先读取当前计时器再修改它，因此正常轮询、Agent 重启以及丢失的 SET 响应都不会重启一个匹配的倒计时。取消或推迟最早的任务可能会留下一次更早的无害唤醒；只有到期的任务才会执行。
当例行任务持有计时器时，HTTP MCU 计时器修改端点会返回 `409 CONFLICT`。直接使用 UDS 的客户端也必须遵守这一归属；MCU 协议没有按客户端划分的计时器租约。

重复投递的唤醒不会重新运行已完成的某次执行。延迟的例行任务只运行一次，并跳过错过的间隔，保持其原有节奏。一次运行失败会停止该例行任务，直到它被显式更新。在执行期间优雅关闭会记录为 `interrupted`，并保留任何部分结果。崩溃后的恢复也会把未完成的执行标记为 `interrupted`。两种情况都不会自动重放可能已完成的设备操作。更新该例行任务前，请先检查会话。这同样适用于正在等待后台运行时空闲的运行中执行；仍在队列中的工作在重启后会保留。
这些规则并不保证外部副作用恰好只发生一次。

MCU 倒计时不是有电池供电的日历闹钟，MCU 断电后不会保留。持久化的定时任务会在 Agent 和 MCU 重新可用时进行对账。Agent 不会为了定时工作而关闭设备电源或烧录设备。关于硬件唤醒和事件投递的限制，参见 [MCU 服务](../04-services/mcu-service.md)。
