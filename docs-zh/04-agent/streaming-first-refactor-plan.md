# 流式优先 Agent 重构：调研与实施计划

**状态：** 范围已根据产品反馈确定；保持兼容性的第 1 阶段基础设施和播放队列加固已在本分支中实现。其余的产品策略和后续迁移阶段尚未获批。

**调研日期：** 2026-10-29。

**仓库基线：** `3aa92741d`，以及当日检查的工作树。

**范围：** **在现有 Go/C++ 运行时内部**的流式 LLM、STT、TTS、实时、工具/任务进度、Web 文本/事件、对话状态以及音频服务边界。所有产品语音输入都来自开发板麦克风。浏览器、手机和桌面麦克风，浏览器/手机实时音频，以及替换或托管的 Agent 运行时都不在范围内。现有的桌面播放仍只是输出侧的开发/回归测试关注点，而不是另一个麦克风来源。这不是对 BSP、MCU 固件、OTA 系统或无关硬件服务的重写。

## 1. 建议

把 Aico 重构为一个**流式优先的对话运行时**，保留现有的 Go 守护进程、C++ 音频服务、提供商适配器、工具和记忆平面。使用**一套共享的生命周期和交付契约**，并配备两个一等引擎：

1. **级联语音：** 流式 STT → LLM/工具循环 → 流式 TTS。
2. **原生实时语音：** 提供商的双向语音到语音会话。

文本聊天使用同一个 LLM/工具引擎，只是不涉及音频。两个引擎共享会话所有权、事件标识、取消、呈现、历史投影和可观测性；它们并不假装拥有相同的提供商协议。

项目**并不**需要从零开始添加流式能力。它已经能够流式处理 LLM 文本、TTS 音频、实时事件和开发板播放。主要的缺口在于：完成/取消语义不一致、STT 只输出最终结果，以及开发板音频的交付/背压契约薄弱。桌面播放同样是缓冲式的；它的流式改造只涉及开发/回归测试输出。

借鉴 LiveKit 的会话/轮次模型、Pipecat 的可中断帧，以及原生实时 API 的响应/条目标识等设计经验。**在本计划的任何阶段都不要替换现有运行时，也不要把它的语音编排外包出去。** Go/C++ 流式核心是唯一的实现选项；外部框架和产品只是调研参考，而不是采用候选。

### 成功意味着什么

- 用户能在文本和临时转写可用时立即看到它们。
- 在支持流式的配置下，用户在生成结束之前就能听到音频。
- 打断会迅速停止本地播放，取消符合条件的上游工作，并且旧音频不会泄漏到下一个响应中。
- 转写假设、生成的内容、已完成的模型响应以及已呈现/已播放的内容，各自具有不同且明确的含义。
- 慢客户端、慢扬声器、提供商故障和重连都有有界的内存/延迟行为，而不是静默丢失或无界缓冲。
- 仅支持批处理的提供商仍然可用，但会被明确标记为降级；把一个已完成的结果包装成流，并不能让它成为低延迟流。
- 现有的工具安全、前台/后台隔离、上下文压缩、提供商特定的消息元数据以及配置兼容性都得以保留。

### 建议的首次交付

落地一个**纵向的流式切片**，而不是在整个仓库范围内重命名接口：开发板麦克风语音 / Web 文本 → LLM 增量 → 语音文本投影 → TTS PCM → 开发板播放，并支持打断和感知交付的收尾。把现有的桌面播放后端作为开发输出端来使用，而不是采集来源。在后续切片中加入来自开发板麦克风的增量 STT，并把原生实时迁移到同一个生命周期上。

## 2. 依据与局限

本提案结合了静态代码检查与当前官方的产品/API 和框架文档。第 15 节中的来源是具有代表性的成熟系统，**并非基于测量的市场份额排名**。商业产品文档描述的是对外暴露的行为，不一定是内部架构。

没有进行提供商延迟基准测试、硬件声学测试或真实提供商兼容性测试。下文中的数字预算是**提议的验收目标**，而不是实测性能或供应商保证。持续更新的文档可能会变化；实现必须为每个适配器固定模型/API 版本，并保留协议测试夹具。不要仅仅因为某个调研页面展示了更新的模型就更改模型默认值。

## 3. 当前架构与具体缺口

### 3.1 当前路径

```text
Classic voice
  device PCM capture ──> optional streaming STT upload
                  └──> local VAD / complete utterance fallback
  final transcript ──> Runtime.Run / AgentLoop
  LLM callbacks ──> leading <tts> parser ──> TTS adapter ──> playback
  complete LLM response ──> tool parsing / history / next iteration

Native realtime
  device PCM <──> realtimevoice managed provider session
  normalized events ──> daemon session loop
                    ├──> playback
                    ├──> chat deltas / completed conversation history
                    └──> foreground tools ──> independent background tasks

Web
  POST /api/chat ──> NDJSON text/progress events
  GET /api/events ──> SSE observer events
  audio attachments / archived audio ≠ live bidirectional browser audio
```

这是对当前行为的盘点，而不是目标范围。现有的音频附件和本地录音并不意味着重构中允许其他语音输入来源；目标来源只有开发板麦克风。

### 3.2 审查发现

| 组件 | 观察到的实现 | 后果与迁移目标 |
| --- | --- | --- |
| LLM | 存在 writer 时，[运行时流式接线](../../src/agent/internal/agent/runtime.go#L1156) 会提供 `llms` 回调。[OpenAI 兼容解码器](../../src/agent/internal/agent/openai_compatible_model.go#L739) 也会组装最终响应。 | 为历史和工具保留最终聚合；用类型化的响应事件取代仅限文本的回调耦合。聚合本身并不是流式缺陷。 |
| Agent 循环 | [生成和解析](../../src/agent/internal/agent/agent_loop.go#L256) 会等待完整的 `ContentResponse`，然后才决定是否执行工具。 | 尽早暴露进度，但绝不执行不完整的工具参数。保留现有的校验和策略边界。 |

| STT 启动 | [异步初始化](../../src/agent/internal/agent/audio_dialog.go#L361) 和 [分块上传](../../src/agent/internal/agent/audio_dialog.go#L496) 在上传器尚不存在时不会上传早期的分块。 | 一个就绪的流可能漏掉开头的语音而不报错。增加有界的就绪前采集和明确的就绪屏障。 |
| 批处理 STT | [`TranscribeWAV`](../../src/agent/internal/agent/stt.go#L66) 缺少 context 参数，使用的请求没有绑定到轮次 context。 | context 取消必须传递到 HTTP 请求和回退转写，而不仅仅是流式路径。 |

| TTS 兼容性 | [语音投影](../../src/agent/internal/agent/speech/text.go#L198) 解析开头的 `<tts>` 块；[OpenRouter TTS](../../src/agent/internal/agent/tts/adapters/openrouter/session.go#L195) 读取完整的 PCM 响应。 | 保留语音/显示分离。报告实际的流式粒度，而不是把每个适配器都宣传为等价的。 |
| 实时 | [`realtimevoice.Session` 和事件](../../src/agent/internal/agent/realtimevoice/interface.go#L199) 已经对提供商行为做了规范化，并暴露可选能力。 | 复用注册表、原生适配器、托管重采样和能力检测。从守护进程编排中提取共享的生命周期策略，而不是提取提供商的线路协议逻辑。 |
| 实时编排 | [守护进程事件循环](../../src/agent/cmd/daemon/realtime_wakeup.go#L1444) 负责准入、历史、播放、工具、通知和聊天桥接。 | 逐步把策略迁移到可测试的控制器中；保留响应 ID 过滤、取消确认、看门狗以及提供商特定的排序规则。 |
| 开发板播放 | [`AudioPlaybackSession`](../../src/audio_playback_session.cpp#L66) 在收尾之前就播放分块；队列满时等待 200 毫秒，然后不重新检查上限就继续推入。 | 保留实际的流式能力；强制执行硬性的时长/字节上限，并明确饱和时的行为。 |
| 采集队列 | [录音队列插入](../../src/audio_record_session.cpp#L241) 在达到 512 个分块的上限时会静默跳过新分块。 | 增加丢失计数、序列/时间元数据，以及明确的不连续处理策略。分块数量上限不等于延迟预算。 |
| 现有桌面播放 | [`local_audio_playback.go`](../../src/agent/internal/agent/local_audio_playback.go#L64) 会先缓存一个 WAV，只在收尾时启动操作系统播放器。 | 把这个开发/回归测试输出端演进为实时 PCM；保留一个带标记的缓冲式回退。这并不意味着允许桌面麦克风输入。 |
| Web 交付 | [聊天 fetch](../../src/agent/internal/agent/web_ui/scripts/chat.js#L33) 使用 NDJSON。[`EventBroadcaster`](../../src/agent/internal/agent/event_broadcaster.go#L21) 有意设计为尽力而为，订阅者通道已满时会丢弃事件。 | 保持 NDJSON/SSE 兼容性。增加标识、重新同步和丢失检测；不要把观察者广播器用作权威的媒体/控制路径。 |
| 手机桥接 | [桥接契约](phone-bridge.md#通信方式) 是命令/结果，而不是麦克风/扬声器媒体协议。 | 保持其仅用于命令/结果；手机麦克风采集和媒体传输是被排除的，而不是推迟的功能。 |
| 后台工作 | [前台/后台分离](foreground-background-agents.md) 把实时对话与排队的设备任务隔离开。 | 保留任务所有权和取消范围；取消语音不得静默取消一个独立的任务。 |
| 遥测 | [Episode 导出器](telemetry-langfuse.md#数据流) 已经使用异步 OTLP 导出。 | 在现有 span 上扩展流里程碑和交付结果；不要引入第二套遥测栈或逐音频帧的 trace。 |

当前的 [语音文档](audio-features.md#tts-提供商用法) 已经说明 TTS 接受 LLM 片段。基于“一切都是阻塞的”这一假设的计划，会丢弃可用的行为，并错过真正的缺口。

## 4. 市场与框架调研

### 4.1 对比与经验

| 系统 / 类别 | 文档记载的模式 | 在 Aico 中应用的模式 | 不要盲目假设或照搬 |
| --- | --- | --- | --- |
| **LiveKit Agents — 语音框架** [S1] | 由会话编排媒体、流水线或实时模型、轮次、打断和事件。轮次检测可以由模型、STT、VAD、实时会话驱动，也可以手动驱动。 | 一个对输入/轮次/输出所有权有明确划分的会话控制器；把可配置的端点检测和打断作为不同的策略。 | SFU、迁移到 Python/Node worker 以及云端部署，都不是单个设备端扬声器的前提条件。 |
| **Pipecat — 语音流水线框架** [S2] | 类型化的帧；紧急的打断帧绕过普通工作，取消符合条件的生成/工具，清空 TTS，并冲掉未播放的输出。其上下文聚合会跟踪已说出的输出。 | 把紧急控制与排队的媒体分开；打断整个输出路径；区分已生成的文本和已播放的文本。 | 通用的处理器图对 Aico 的每个操作来说并非必要。精确跟踪已播放的词需要真实的对齐和播放证据。 |
| **OpenAI Realtime / Agents SDK — 原生语音模型和 SDK** [S3] | 有状态的响应/条目事件，流式音频/文本，VAD 或语义 VAD；浏览器 WebRTC 以及服务器/自定义音频 WebSocket 路径。 | 响应/条目关联；提供商就绪门控；取消/截断支持以及提供商能力契约。 | OpenAI 风格的 JSON 并不是通用协议；WebSocket 客户端仍需自行管理播放队列和进度统计。 |
| **Gemini Live — 原生语音模型** [S4] | 双向 WebSocket，具有不同的生成完成、轮次完成、被打断、工具和转写信号。 | 区分各个完成里程碑；处理每条提供商消息的所有部分；保留原生的取消和上下文行为。 | 提供商维护的已发送内容历史，并不能证明音频确实已在设备上播放。 |
| **Azure Voice Live — 托管实时服务** [S5] | 带版本的会话/事件 API，轮次检测配置，流式的函数参数和输出。 | 固定协议版本，并显式协商功能。 | 预览版 API 中的功能不能推断为另一个版本或所有模型/区域也具备。 |
| **Vapi — 托管语音 Agent 平台** [S6] | 会话/通话事件信封，关联的工具和模型输出；WebSocket 媒体与服务器 webhook 事件相互独立。 | 清晰的控制/媒体分离，以及按轮次的事件标识。 | webhook 不是低延迟的媒体路径；暴露的 API 并不能确立内部的背压保证。 |
| **Retell AI — 托管语音 Agent 平台** [S7] | 自定义 LLM WebSocket 提供实时转写和 `response_id`；更新的请求会使之前的响应失效。 | 生成失效以及取消过期的模型工作；衡量到第一个有用语音片段的时间，而不仅仅是第一个 token。 | 自定义 LLM 集成仍然把响应延迟、可用性和重连留给应用负责。 |
| **ElevenLabs Agents / Speech Engine — 托管语音栈** [S8] | 类型化的转写/响应/音频/打断事件；Speech Engine 支持应用自有的流式 LLM，并在新的转写事件到达时取消。 | 分别维护已生成、已更正和已交付的响应状态；让播放队列显式化。 | 流式文本并不能消除对客户端播放缓冲或能力检查的需要。 |
| **LangChain / LangGraph — 通用 Agent 编排** [S9] | 针对消息文本、工具参数/执行、状态、子 Agent、自定义进度和最终输出的各自独立的投影。 | 在一次运行之上做类型化投影，而不是若干互不相关的回调路径。 | 工作流/token 流不是声学轮次检测器，也不是媒体调度器。本计划不提议用 Python 重写。 |
| **Dify — 通用 Agent 产品** [S10] | SSE Agent 增量、工具/进度事件、一条完整的最终消息，然后是一个终止标记。语音端点是独立的。 | 用最终快照来校正增量；区分任务进度和最终响应。 | 流式聊天 API 加上文件式 STT/TTS 并不等于全双工语音。 |
| **Deepgram — 流式语音组件** [S11] | 临时假设可能会改变；`is_final` 表示一个分段已定稿，而 `speech_final` 标识一个话语边界。 | 区分转写修订、分段定稿和轮次完成。 | 不要为每个临时转写都启动工具，也不要把任意定稿分段等同于用户轮次已完成。 |
| **Alibaba/Qwen — 相关的区域性语音提供商** [S12] | 实时 STT 有就绪/任务边界；TTS 支持增量文本、flush 和收尾；实时语音有原生的轮次模式和事件。 | 就绪缓冲、显式 flush/finish、原生适配器，以及中文/区域验证。 | Qwen ASR、Qwen TTS 模型系列和 Qwen 实时语音并不共享一个可互换的协议。 |

### 4.2 共同的架构结论

1. **流式是一种生命周期，而不是传输开关。** SSE/NDJSON/WebSocket 只负责搬运字节；它们并不定义打断或完成时的正确性。
2. **对话与执行是两回事。** 一个响应迅速的前台语音会话不能同步等待耗时较长的设备操作。
3. **STT、LLM 和 TTS 是不对称的。** STT 会修订假设；LLM 输出文本和结构化的工具数据；TTS 消费已提交的语音单元并输出音频。
4. **生成完成不等于播放完成。** 一个响应可能已经生成完毕，但还剩下数秒尚未播放的音频。
5. **提供商能力的差异是契约的一部分。** 规范化的是概念，而不是每一个线路操作或不受支持的功能。
6. **取消和背压从第一天起就属于架构的一部分。** 一个名为 `Stream` 的接口并不足以证明延迟是有界的。

### 4.3 选定的实施边界

**只有现有 Go/C++ 系统内部的流式核心在范围之内。** 它保留已部署的设备服务、Agent 工具/记忆以及提供商适配器，而 Aico 负责生命周期和协议测试。额外的回调只是过渡性的垫片，而不是一套永久并行的架构。LiveKit、Pipecat、Vapi、Retell 和 ElevenLabs 仍然只是第 4.1 节中的设计依据来源，而不是本计划中的替代运行时或托管语音通道。不计划引入 WebRTC 网关、浏览器/手机媒体传输或桌面麦克风。

## 5. 目标架构与所有权

```text
Inputs
  Board microphone PCM     Web text (no live media)
            │                        │
            └────────────┬───────────┘
                           │
                 Conversation controller
             admission, turn policy, output epoch,
              interruption, reconnect, config snapshot
                           │
             ┌─────────────┴─────────────┐
             │                           │
       Cascaded engine             Native realtime engine
       STT event session           existing realtimevoice adapters
       LLM/tool run                native audio / text / tools
       spoken-text projection
       TTS session
             │                           │
             └─────────────┬─────────────┘
                           │
             Typed semantic events + audio frames
                           │
              Presentation / playback coordinator
                           │
              Board speaker / desktop development sink
                           │
                  Playback progress receipts

Read-only projections: web events, history, task progress, episode telemetry
Independent execution: agenttask queue + existing backend Runtime and tools
```

### 所有权规则

- 一个控制器负责一个对话的准入和生命周期转换。只有一个麦克风/扬声器的设备只有一个前台媒体所有者；本提案并不意味着支持无限数量的同时对话。
- 开发板麦克风是唯一的产品语音输入生产者，其使用方有明确的上限。VAD 分支使用 16 kHz、512 采样的帧；STT/实时分支使用协商的格式。Web 文本永远不会变成 PCM。
- 运行负责模型尝试和工具调用。呈现协调器负责扬声器的排序、优先级、停止、排空和交付回执。
- 用户回复优先于排队的通知。任务更新和通知保留现有的空闲准入和隐私规则；它们不会混入每一条助手文本流。
- 提供商负责认证、传输分帧、原生事件转换以及协议特定的能力。它们不直接写入 Web 历史。
- 历史投影持久化已提交的对话记录。另一份独立的交付记录说明哪些内容已显示/已播放、被打断或状态未知。
- 遥测和观察者客户端不能阻塞麦克风采集或播放。

### 包边界（不立即调整目录结构）

引入一个小的叶子包，暂定名为 `internal/stream`，用于存放值类型、ID、终态/错误约定、音频帧元数据以及有界队列辅助工具。它不得导入 `agent`、任何提供商 SDK 或 HTTP 处理器。

把控制器逐步提取到 `internal/voice` 之类的包中，它依赖窄接口和叶子类型，而不依赖 `agent.Runtime` 的具体内部实现。守护进程仍然是组装根，并为运行时、历史、工具、播放和 `agenttask` 提供适配器。现有的 `tts`、`speech` 和 `realtimevoice` 包保持原位，直到移动它们能带来具体的好处。在提取守护进程循环时避免引入导入循环。

这**不是**一个通用事件总线框架、分布式事件存储、Kafka 流水线或任意图执行器。热路径上使用直接的类型化连接，只在投影中使用订阅。

## 6. 共享的流式契约

### 6.1 标识与排序

一个语义事件拥有一个带版本的信封，以及恰好一个类型化的负载：

| 字段 | 含义 |
| --- | --- |
| `schema_version` | 对外的事件 schema；提议的首个新版本为 `2` |
| `event_id`, `sequence` | 稳定的事件标识，以及在一个对话 epoch 内由控制器分配的序号；重放游标同时包含 epoch 和序号 |
| `conversation_id`, `session_epoch` | 持久的对话，以及当前实时连接的代次；重连会推进 epoch |
| `turn_id`, `run_id` | 被接受的用户轮次和执行；一次运行可能包含多个模型响应/工具 |
| `response_id`, `attempt_id`, `item_id` | 一个模型响应、一次尝试和一个内容条目；重试时绝不复用尝试标识 |
| `stream_id`, `output_epoch` | 输出轨道及其失效代次；输出停止时输入采集不会失效 |
| `call_id`, `task_id`, `parent_id` | 可选的工具/后台工作关联 |
| `occurred_at`, `received_at` | 提供商时间戳（可用时）和本地接收时间；时长使用本地单调时钟计算 |
| `origin`, `visibility` | 提供商/模块来源以及允许的投影：用户显示、语音、内部或诊断 |

并不是每个事件都需要所有可选 ID。按事件类型强制要求必填字段。提供商的 ID 仍作为元数据保留；对于不提供 ID 的提供商，由适配器分配本地标识。不要根据到达时间推断全局的提供商顺序，也不要伪造缺失的语音边界事件。

音频走一条独立的二进制/数据路径，带有相同的关联 ID、`frame_seq`、格式、采样数以及以**每声道采样数**计的呈现位置。不要对内部 PCM 做 base64 编码，也不要把每一个 PCM 帧都作为历史事件发出。测量延迟时，不直接相减不同机器的时钟。

为了实现 Web 重新同步，以原子方式获取活跃轮次的快照及其事件水位线，然后交付该水位线之后的事件。各投影专用的游标必须考虑过滤：一个被省略的内部事件并不是丢失的公开事件。进程重启会使临时的重放窗口失效，需要新的快照；不得复用旧的 epoch/游标组合。

### 6.2 事件族

| 族 | 代表性事件 | 重要语义 |
| --- | --- | --- |
| 会话 | `session.ready`, `session.reconnecting`, `session.closed` | ready 表示协商的配置已被接受，而不仅仅是 socket 已连接 |
| 输入 | `input.speech_started`, `input.speech_stopped`, `transcript.updated`, `transcript.segment_final`, `turn.committed` | 临时文本可以被修订；分段定稿与用户轮次完成是两回事 |
| 模型 | `response.started`, `text.delta`, `text.final`, `tool.arguments_delta`, `tool.call_ready`, `response.terminal` | 最终快照替换/校正其增量，绝不会再次追加完整文本 |
| 语音 | `speech.text_committed`, `audio.started`, `audio.ended` | 只有被批准用于语音的文本才会进入 TTS；音频结束是生产结束，而不是播放排空 |
| 呈现 | `playback.started`, `playback.progress`, `playback.drained`, `playback.stopped` | 回执包含 epoch、条目、已播放位置以及置信度/测量来源 |
| 工作 | `tool.started`, `tool.progress`, `tool.completed`, `tool.failed`, `task.updated` | 进度是可选的；最终结果保持关联且有界 |
| 控制 | `cancel.requested`, `cancel.acknowledged`, `stream.discontinuity`, `stream.error`, `usage.updated` | 取消可以绕过排队的数据；错误区分可恢复和终态两种范围 |
| 运行 | `run.terminal` | 执行完成与呈现完成是不同的 |

把提供商暴露的推理内容和签名/不透明元数据与可见文本和语音分开。保留当前的重放要求和允许的推理显示设置，但不要让原始推理成为必需的公开流或遥测要求。

### 6.3 生命周期不变式

1. 每次响应尝试、合成、工具调用和运行，都在内部记录唯一一个终态结果：`completed`、`cancelled` 或 `failed`。
2. 通道关闭 / EOF 但没有终态结果，视为失败，而不是成功。
3. 已失效 epoch 的迟到输出不会到达用户或新的响应。迟到的用量只能更新计量，不能让输出或看门狗复活。
4. `FinishInput` 是半关闭：待处理的输出仍可能到达。
5. `Flush` 提交当前缓冲的语音文本，但不结束输入。
6. `Cancel` 请求及时终止；它并不能证明远端已确认或播放已停止。这两个结果分别观察。
7. `Close` 是幂等的资源释放，而不是一个身兼收尾/排空的重载调用。如果工作仍在进行，它会发起取消并使用有界的关闭截止时间；它不能无限等待某个使用方排空一个已被遗弃的通道。
8. 正常的结束屏障包含最后一个相关的序号/帧位置，不能超越之前的数据。紧急的取消/错误信号可以绕过数据，因为它们明确使这些数据失效。
9. 每一个阻塞的发送/读取/写入都有 context 或截止时间。每个通道由唯一一个所有者关闭；所有权释放之后，生产者不能再发送。
10. 恰好一次的状态转换是本地不变式，**并不是对恰好一次网络交付的承诺**。重放的事件可能重复；由使用方去重。

### 6.4 接口方向

以下是设计草图，而不是可直接复制粘贴的补丁提案。`ModelRequest`、`TranscriptEvent` 和 `AudioFrame` 等类型仍然各自针对特定模态。

```go
// Runtime output is streamed while this call runs; final state remains available.
type Runner interface {
    RunStream(context.Context, TurnInput, EventSink) (RunResult, error)
}

type EventSink interface {
    Emit(context.Context, Event) error
}

type RecognizerSession interface {
    WriteAudio(context.Context, AudioFrame) error
    FinishInput(context.Context) error
    Events() <-chan TranscriptEvent
    Cancel(context.Context) error
    Close() error
}

type SynthesisSession interface {
    WriteText(context.Context, SpeechText) error
    Flush(context.Context) error
    FinishInput(context.Context) error
    Events() <-chan SynthesisEvent
    Cancel(context.Context) error
    Close() error
}

type Playback interface {
    WriteAudio(context.Context, AudioFrame) error
    FinishInput(context.Context) error
    Progress() <-chan PlaybackEvent
    Stop(context.Context, StopReason) error
    Close() error
}
```

保留原生实时的双向会话和可选操作；不要强行让它通过 `RecognizerSession` 加 `SynthesisSession`。把它的事件桥接到共享契约中。在更简单的情况下，TTS 音频可以继续使用类型化的输出端而不是事件通道；无论采用哪种表示，生命周期和所有权语义都必须一致。

对于兼容的调用方，阻塞式 API 继续作为新流之上的收集器存在。在迁移期间保留 `Runtime.Run`、`TranscribeWAV` 和旧的 HTTP 响应形式。仅支持批处理的实现使用有界适配器，并声明 `output_granularity=final_only`；不要发出伪造的增量 token。

## 7. 逐模块改动

### 7.1 LLM 与 Agent/工具循环

- 为文本、暴露的推理、工具参数增量、工具调用就绪、用量、错误和终态引入类型化的模型事件。保留最终响应聚合、提供商特定的上下文、缓存元数据和签名推理。
- 让所有前台模型调用在内部原生支持流式。后台压缩、记忆提取和其他非交互式调用可以收集整个流；它们的事件保持在内部，不得发声或进入聊天历史。
- 把输出的作用域限定在一个响应/条目上，而不是一个可变的全局文本缓冲区。保留工具循环迭代之间以及引导之间的重置/中止/结束边界。
- 按调用 ID 和索引组装参数。只有完整、有效、通过 schema 检查且经策略批准的调用才可执行。最初保留当前在响应终态时执行的边界；在调用完整后提前执行是之后的优化，需要显式的副作用测试。
- 在支持的地方发出工具生命周期事件和有界的进度。一个原子的 HID 操作只能如实地发出开始/结果；“所有模块都流式化”并不要求伪造进度，也不要求为每个工具新写一套流式实现。
- 保留现有的取消/抢占通知、运行预算、上下文溢出恢复以及前台/后台任务语义。

**重试规则：** 在产生外部可见输出之前以及产生副作用之前，按照现有重试策略自动重试是安全的。文本已经显示之后，在替换之前要先标记/校正失败的尝试。音频已经播放之后，绝不能透明地从头重放答案。只有在提供商的支持经过验证，或明确发起一个新响应时才能续接；否则报告部分失败。副作用结果未知的情况永远不会自动重试。

### 7.2 STT 与输入轮次检测

为音频流式输入、临时结果、分段定稿、提供商端点检测、词级时间戳以及取消/恢复支持分别增加独立的能力字段。不要从 `SupportsStreamingUpload` 推断转写支持流式。

使用带修订号的转写分段：

```text
segment_id, revision, text_snapshot, is_final,
audio_start_sample, audio_end_sample,
optional stable_prefix / word timings / language / confidence
```

更新的快照会替换该分段之前的假设。空快照可以撤回一个假设。只有已提交的定稿才会进入持久的用户历史；定稿分段由一个配置的轮次权威组装成一个轮次。

- 尽早开始准备连接，但只有在提供商就绪之后才释放音频。保留一个有界的就绪前队列，其中包含开头的语音前缀。
- 如果就绪时间超出预算，显式切换到有界的批处理回退，或让该输入轮次失败。绝不能静默跳过前缀，然后接受一个不完整却“成功”的转写。只以提供商允许的速率重放排队的音频。
- 保留本地 VAD 用于活动检测和经典端点检测；只有在被选中时才使用提供商或语义端点检测。在需要时，原生实时仍以提供商为权威。不要对同一输入运行相互竞争的轮次提交者。
- 把临时字幕流式推送到 UI。默认：只有在轮次提交之后才启动权威的 LLM/工具运行。之后可以探索可选的推测式生成，但在被接受之前不得有工具副作用、不得提交历史、不得有可听见的输出；需要衡量浪费的 token 和错误的端点。
- 增加感知 context 的批处理转写。对话语时长、字节数、建立时间、收尾时间和回退尝试次数设置上限。定义无语音、转写不确定、仅有噪声的打断以及部分网络丢失时的行为。

### 7.3 语音文本投影与 TTS

保留现有的**语音文本与显示文本**之间的区分。在迁移期间，开头的 `<tts>...</tts>` 解析器会发出 `speech.text_committed` 分段；它是针对当前模型输出格式的适配器，而不是每个下游组件都要各自解析的协议。

不要同时修改提示词和流式基础设施。之后对提示词格式的修改需要单独做多语言质量评估。语音最终采用结构化内容还是显式标记的文本，与流契约无关。

- 规范化分块边界，不切断 UTF-8 序列。在有意修改之前，保留当前针对被拆分的标签、缺失的闭合标签、工具响应边界、多余的标签以及重复语音抑制的行为。
- 为需要文本单元的适配器保留一个共享的、可配置的句子/分句切分器。处理中文标点、缩写、数字、URL、Markdown、代码块以及未闭合的结构化内容。绝不朗读工具 JSON 或内部推理。最大等待时间只能冲刷一个安全的语音单元，而不能冲刷任意的部分标记或正在生成中的数字。
- 区分原生增量文本 TTS、句子输入/音频流式 TTS 以及批量合成。提供商特定的缓冲和韵律控制留在适配器内部，但要暴露它们的实际粒度和首个音频里程碑。
- 把当前的关闭行为拆分为输入结束、合成结束、播放排空和关闭。不要让提供商的读取循环因为扬声器缓慢而无限阻塞。
- 保留提供商持有者的生命周期规则：配置变更只影响新的会话；现有会话要么正常结束，要么被显式取消，绝不会在一句话说到一半时静默更换音色/模型。
- 保留通知尾音、本地回退音频片段和工具调用语音规则。私密通知的语音是一个单独的呈现条目。在部分语音已播出后发生的失败，不得把整个响应作为回退重新播放。

### 7.4 实时语音

复用现有的提供商注册表、原生转换器、媒体协商、托管重采样和可选接口。本次重构主要是提取共享的控制器/呈现职责，而不是替换可用的适配器。

- 把原生的响应/条目/工具 ID 映射到共享标识，并保留重放、用量、打断和截断所需的原生信息。
- 区分生成结束、提供商轮次结束、输入转写定稿以及本地播放排空。某些原生事件可能缺失或乱序。
- 保持取消确认和无进展看门狗行为；后台的麦克风流量不得让一个卡住的响应一直存活。
- 使用已确认或明确估算的播放位置来打断/截断，绝不能简单使用已提交给输出端的字节数。如果打断后无法使提供商上下文保持一致，就保守地重连/重放。
- 不要把实时输入转写作为第二个提示词重新提交。它们是提供商已经消费的音频在用户侧的投影。
- 保留提供商特定的工具续接。只执行完整且经过校验的调用，关联并行结果，并处理被提供商取消的调用 ID。
- 在重连/会话轮换时，保留对话 ID，推进连接 epoch，恢复已提交的上下文，并且不重放过期的音频或工具操作。只有在提供商声明并验证支持会话恢复时才使用它。

### 7.5 开发板采集、音频格式与播放

保留现有的二进制负载 UDS 协议，而不是通过 JSON 发送 PCM。为帧序号、采集时间戳、排队时长、丢帧数、已播放位置以及显式的停止/排空确认，增加向后兼容的字段/能力协商。旧的客户端和服务必须继续能够互操作。

PCM16 小端单声道是初始的内部基线。**不要**强制每个提供商都使用 16 kHz：保留协商得到的提供商/设备采样率，只在边界处重采样。在帧之间保持有状态的重采样器；在 epoch 变化时有意地重置/冲刷，并处理奇数字节的碎片。在每个流描述符中加入编解码器/声道/采样率元数据，而不是在调用方中做隐式假设。

- 同时按字节数**和音频时长**强制执行播放上限，每次等待后重新检查。饱和时必须产生有界的等待或明确的错误，而不是额外的无界推入。
- 采集不能无限等待远端的使用方。优先采用有界的、保持新鲜度的丢弃最旧数据的行为，并配合不连续计数器；如果缺口使某个轮次失效，再重置/失败受影响的识别。绝不能把损坏的输入呈现为可靠的完整转写。
- 区分被服务接受的数据、已提交给硬件的数据，以及估算或已确认渲染的采样。当前的硬件尾部宽限期并不是精确的播放时钟。声明置信度；用回环/声学测试进行验证。
- 把桌面的整段 WAV 播放演进为用于开发和输出回归测试的实时 PCM 输出端，支持显式的停止/排空，并在需要时提供带标记的缓冲式回退。这只是输出方面的事项：不要增加桌面麦克风采集，也不要把仅基于文件的回退描述为实时。
- 保留 Rockchip VQE/AEC 流水线。在同时采集/播放通过板上回声和误触发测试之前，经典的全双工插话（barge-in）保持为需要主动开启的选项。硬件按键仍然是可靠的打断路径。

### 7.6 Web 文本、手机命令与后台使用方

**文本 API：** 保留当前的 NDJSON `/api/chat` 和 SSE `/api/events`。增加一个显式的 v2 协商选项；两种传输序列化同一个语义投影，而不是各自发明不同的事件类型。通过收集器让现有的非流式客户端继续工作。最终快照是替换，而不是增量。

定义请求所有权：拥有请求的聊天连接在断开时，可以按照现有产品行为取消其请求；观察者 SSE 断开绝不能取消一次运行。显式取消针对的是请求/运行/响应 ID，而不是“当前正在活跃的任何东西”。慢速观察者会收到 `resync_required`，或者被断开连接后重新加载历史以及活跃轮次快照。使用带游标/epoch 的有界重放窗口；在重启或游标过期后，请求一个快照，而不是承诺无限的事件重放。

**语音输入边界：** 由 `audio_service` 暴露的开发板麦克风是唯一的产品语音输入来源。浏览器麦克风采集、浏览器实时音频、手机麦克风/媒体传输以及桌面麦克风采集，永久不在本计划范围内。Web UI 仍然只是一个文本/事件客户端；Phone Bridge 仍然只用于命令/结果。不要在此架构下为这些客户端增加未来的媒体会话扩展。

**后台使用方：** 任务、MCP/HTTP 工具调用方、调度器、记忆工作和基准测试会消费相关的运行/进度投影。它们不需要消费 PCM。保留现有的任务 ID、引导、上下文谱系和取消所有权。工具进度不应自动变成语音；由前台决定何时以及如何概括它。

## 8. 打断、状态与历史的正确性

### 8.1 状态不是一个线性枚举

对话可以一边说话一边聆听。分别跟踪相互正交的状态：

| 状态域 | 状态 |
| --- | --- |
| 连接 | opening → ready → reconnecting / closing → closed |
| 输入轮次 | idle → speech / hypothesis → committed 或 discarded |
| 生成 | idle → running → cancelling → terminal |
| 播放 | idle → buffering / playing → draining → drained，或 stopped |
| 后台任务 | 现有的、独立的 `agenttask` 生命周期 |

一个响应可能已经到达终态，而播放仍在进行。播放期间也可能采集到新的话语。由控制器决定准入；这些事实不能被压缩成一个含义模糊的 `busy` 标志。

### 8.2 插话事务

1. 本地/提供商的轮次策略接受一次打断（并非每一次能量尖峰都算）。
2. 以原子方式使当前输出 epoch 失效，使迟到的数据包变为过期。
3. 立即停止/冲刷本地播放；不要等待提供商的网络往返。记录已播放的位置，以及它是测量值还是估算值。
4. 取消 LLM/TTS/符合条件的前台工具，并在支持的地方发送原生的响应取消或截断请求。除非用户显式取消或更新后台任务，否则后台任务会继续运行。
5. 分别记录本地停止和远端终态的结果。在等待提供商必需的取消确认期间，保留准入所有权。
6. 提交感知交付的部分记录和打断原因；只有在安全时才准入下一个响应。缺失的确认超时后转为重连。
7. 对于误打断/没有转写的情况，遵循明确的产品策略：只有在能够安全支持时才续播，否则提示用户重复或继续聆听。不要静默地从头重新开始播报。

### 8.3 历史与交付投影

保留当前的用户/后台上下文拆分。增加交付元数据，而不是把每一个瞬时事件都变成持久的对话消息：

- 最终的用户转写是持久的输入。临时假设是短暂的。
- 最终生成的助手内容是文本/历史的规范响应，并带有终态状态和尝试标识。失败的部分输出会被标记，而不会被冒充为已完成的答案。
- 当存在可靠的对齐信息时，语音重放上下文使用已交付的语音/分段。生成的文本单独保留，用于诊断和显示，并与实际说出的内容明确区分。
- 有词级时间戳和播放时钟时，截断到已确认播放的范围。没有它们时，只提交已确认完整的分段，外加一个被打断 / 交付未知的标记。不要按字节比例估算已说出的词并声称其准确。已渲染音频的回执仍不能证明有人听到了。
- 即使语音被取消，也要保留工具调用/结果对以及操作结果。被打断的确认语不会撤销设备操作。
- 通知语音保持私密，并根据实际的播放策略进行确认。它不得泄漏到用户对话的重放中。
- 崩溃时，保留现有的被中断运行恢复机制，并增加未完成交付的状态。恢复期间不要自动重放音频或副作用。

## 9. 背压、错误与恢复

### 9.1 队列类别与临时预算

这些是用于实验的起始值，而不是未经测量就应用的新配置默认值。在 PCM16 单声道下，未计入分帧/拷贝之前，16 kHz 需要 32 KB/s，24 kHz 需要 48 KB/s，48 kHz 需要 96 KB/s。

| 队列 / 操作 | 初始实验预算 | 饱和策略 |
| --- | --- | --- |
| 采集 → STT/实时 | 稳态队列 200–500 毫秒；就绪前缓冲最多 2 秒 | 发出不连续事件，并显式地重置/失败/回退；绝不静默丢失语音前缀 |
| 批处理 STT 回退 | 初始每段话语最多 30 秒，可按产品需求配置 | 以明确的状态结束/拒绝过长的输入；不在内存中无限录音 |
| 等待 TTS 的语音文本 | 限制字节数和估算的语音时长，初始为 2 秒量的排队语音 | 传递有界的背压；如果提供商无法暂停，就显式让响应失败，而不是无限累积 |
| 输出 PCM | 初始播放缓冲 60–120 毫秒；目标排队 <300 毫秒，硬上限 1 秒 | 停止接收、传递压力，然后在截止时间到达时取消；正在播报的句子中不能出现静默空洞 |
| 观察者事件 | 按数量/字节数设上限，并配合活跃轮次快照和有界重放 | 合并可替换的快照，或断开/重新同步；绝不静默丢失终态事件 |
| 控制 | 一个小的预留邮箱加取消信号 | 取消/停止不受媒体队列是否已满的影响；正常结束仍是有序屏障 |
| 会话缓冲总量 | 初始目标为额外的应用层缓冲 ≤8 MiB | 以明确的错误拒绝超出部分；在目标硬件上测量实际的分配/拷贝 |

提供商生成音频的速度可能快于实时，并且可能不支持暂停。仅靠 TCP 流量控制并不能构成应用层面的保证。适配器必须在隐藏的 socket/SDK 缓冲区破坏延迟之前，报告自己跟不上。原生实时提供商可能需要与级联 TTS 不同的调优预算；保持相同的策略类别和经过测量的上限。

### 9.2 错误分类与重试规则

使用带作用域的错误，包含 `code`、`stage`、`retryable`、`response/attempt_id`、`partial_output` 和 `side_effect_state`；对提供商负载做脱敏处理。

| 失败 | 要求的行为 |
| --- | --- |
| 建立/认证/配置 | 在采集/输出之前失败，或显式选择一个已批准的回退；无效凭据不会被无休止地重试 |
| STT 建立截止时间 | 有界的缓冲/批处理回退或输入失败；不能把丢失前缀伪装成成功的流式处理 |
| 输出之前提供商的瞬时故障 | 有限的指数退避加抖动，并共享截止时间；不能出现嵌套重试导致的次数相乘 |
| 部分文本/音频之后的失败 | 标记为部分结果；不要透明地拼接/重放另一次尝试 |
| 下游饱和 | 遵守截止时间；取消相关输出；报告 `backpressure_timeout` 和队列指标 |
| 副作用发生后工具超时/取消 | 独立于语音记录成功/失败/未知；重试前需要幂等支持或对账 |
| 取消之后的提供商事件 | 从呈现中丢弃；只保留允许的计量/诊断 |
| 重连/会话过期 | 推进 epoch；恢复已提交的上下文；只有在提供商支持经过验证时才续接 |
| 遥测不可用 | 继续对话；有界的尽力导出，不阻塞音频线程 |

## 10. 配置、能力与兼容性

继续使用 `model_settings` 和 `voice_settings` 下当前的具名提供商记录。不要引入并行的提供商注册表，也不要把重写用户 TOML 作为前提条件。扩展 Config Web 使用的现有提供商元数据。

能力解析的维度是**提供商 + 模型 + API 版本 + 模式**，在会话就绪时最终确定。区分静态已知的支持和协商得到的支持。向运维人员和测试暴露实际生效的能力以及降级原因：

| 领域 | 能力维度示例 |
| --- | --- |
| LLM | 文本增量、工具参数增量、用量时机、取消、可续接性 |
| STT | 实时音频输入、临时快照、分段定稿、端点检测、词级时间戳 |
| TTS | 增量文本、句子输入、增量 PCM、对齐、flush、取消 |
| 实时 | 轮次权威、打断权威、取消/截断、工具续接、上下文重放/恢复 |
| 播放 | 实时写入、停止、排空、队列时长、已播放位置精度 |

示意性的策略新增项：`streaming_policy = "prefer" | "required" |
"disabled"`、有界的队列/截止时间设置、轮次检测权威，以及全双工/插话模式。名称和放置位置在实现前需要一份配置 ADR；本文并不声称这些键已经存在。

- `prefer`：在支持的地方使用真正的流式处理；明确披露批处理回退。
- `required`：拒绝无法满足所请求流水线（包括其播放输出端）的配置，而不是静默降级。
- `disabled`：兼容性收集器行为，而不是一个单独的永久引擎。

在弃用期间，通过适配器保留现有的 `voice_streaming_tts_enabled`、输入模式、请求 ID、事件名称和 API。热重载使用按会话的配置快照；模式/媒体格式变更会在安全边界处重启。增量式的 UDS 和 HTTP 变更先于客户端发布。回滚后必须仍能读取新写入的历史，并忽略新增的交付数据。

输入来源校验与播放选择相互独立。语音采集必须通过 `audio_service` 使用开发板麦克风；缺少开发板音频时，语音激活必须显式失败，绝不回退到桌面、浏览器或手机麦克风。批处理 STT/回退可以处理在开发板上采集的 PCM/WAV；上传的音频不得成为另一个产品语音来源。保留归档音频查看和隔离的测试夹具，但不要把它们变成实时输入路径。实现必须记录/拒绝不兼容的旧版输入设置；兼容性不能凌驾于这一固定的来源边界之上。本文不改变任何当前已部署的行为。

## 11. 安全与可观测性

### 11.1 安全要求

- 流式数据一旦显示或说出就可能无法撤回。在相应的输出投影**之前**就应用可见性、脱敏和安全策略，而不是只在持久化已完成的响应时才应用。
- 不要朗读原始模型推理、工具参数、凭据或不可信的标记。现有的工具校验/审批仍然具有权威性。
- 为帧、事件、工具参数、转写和缓冲内容设置最大尺寸；在分配内存之前校验长度和格式。
- Web 文本/事件端点需要经过认证的所有权、来源检查、适用时的 TLS、速率限制以及会话范围内的取消权限。提供商密钥保留在服务器端。不计划提供客户端直连提供商的实时媒体路径。
- 音频/转写的保留以及遥测上传都是明确的策略选择。默认不要向遥测添加原始音频上传或私密转写。保留当前需要主动开启的遥测，并对诊断采集做脱敏处理。

### 11.2 指标与 trace 结构

扩展现有的 Episode/OTLP 集成，保留稳定的名称以及按调用的模型/用量归属。保留当前的 OTLP 契约和接入版本；本提案不需要升级 Langfuse SDK 或平台。实现埋点时请参考当前的 Langfuse 指南 [S13]。

按对话对轮次/运行进行分组；关联后台任务，而不是把它们同时作为派发和执行重复记录。有用的阶段包括采集、端点检测、STT、每次模型尝试、工具执行、TTS 和播放。发出摘要和里程碑，而不是每个 token/音频帧一个 span。

至少记录：

- 最后一个用户语音采样、被接受的轮次结束、首个/最终转写。
- LLM 请求、首个可见文本、首个被批准用于语音的文本、最终响应。
- TTS 请求、首个解码的 PCM、首个渲染的音频、最后一个渲染的音频。
- 打断被检测到/被接受、本地停止、远端取消确认。
- 队列时长/字节数、溢出/不连续、欠载、过期事件丢弃。
- 提供商/模型/API 版本、模式、格式、网络区域、token/音频用量、重试、回退、冷/热建立、终态/交付状态以及任务结果。

把 `end_of_user_speech → first_rendered_audio` 作为主要的语音延迟进行报告。同时报告 `turn_commit → first_rendered_audio`，以区分端点检测造成的延迟。不要把提供商的首个音频时间称为“用户感知延迟”。确认语和首个有用答案使用不同的指标，以免填充语被用来钻 SLO 的空子。

### 11.3 提议的验收预算

对于在选定的提供商/模型/区域上、测试网络状况良好时的一个热启动、无工具的轮次，先从以下假设出发；在第 0 阶段建立实际基线：

| 指标 | 初始目标 |
| --- | --- |
| 最后的用户语音 → 首个有用的渲染音频 | p50 ≤1.0 秒，p95 ≤1.8 秒 |
| 被接受的打断 → 开发板播放停止 | p95 ≤150 毫秒 |
| 不含提供商/网络的本地处理开销 | 在目标硬件上每轮 p95 ≤100 毫秒 |
| 首个流式音频与生成结束的关系 | 在支持流式的测试夹具和实测冒烟用例中，音频在响应完成之前开始 |
| 停止确认之后的过期输出 | 来自已失效 epoch 的呈现帧为零 |
| 重复的工具执行 / 重复的语音分段 | 在确定性的故障/重放测试中为零 |
| 会话内存和 goroutine | 队列有界；在 1 小时浸泡测试期间没有持续增长 |

重度使用工具、冷启动、网络降级以及批处理回退的场景分别统计各自的分布。不要因为一个臆造的提供商 SLA 而阻塞版本发布；在建立基线之后批准经过测量的阈值，并明确报告回归。

## 12. 验证策略

### 12.1 先做确定性测试

构建假时钟、脚本化的提供商事件和假的播放回执，使以下测试不依赖网络时序或付费 API：

1. 任意的 token/UTF-8/标签边界；多个工具调用；推理/内容分离；最终快照等于合并后的增量，且没有重复语音。
2. STT 假设替换/撤回；每段话语多个定稿分段；就绪延迟；空语音；建立/收尾失败以及有界回退。
3. TTS 的 flush 与 finish；句子/韵律边界；缓慢的合成/扬声器；奇数字节的 PCM 碎片；重采样器连续性和格式变化。
4. 在首个 token 之前、参数生成期间、合成期间、生成之后但排空之前，以及与响应完成同时发生的打断。
5. 数据队列饱和时取消到达；写入卡住；没有终态的 EOF；重复/乱序的提供商事件；匿名的实时事件。
6. 断开/重连/租约过期、过期的 epoch、缺失的取消确认、可见输出之后的重试，以及交付不确定时的崩溃恢复。
7. 在取消期间完成的工具副作用；并行调用；后台任务的继续执行；引导修订；通知/告别语播放的准入。
8. 新旧 HTTP 和 UDS 的兼容性；慢速 SSE 使用方；快照重新同步；观察者断开与拥有请求的连接断开的区别。
9. 按会话的格式/提供商重载隔离；格式错误的帧和超大负载；并发/竞态测试和 goroutine 泄漏检查。
10. 仅限开发板来源的校验：拒绝其他麦克风/输入设置；缺少 `audio_service` 时绝不选择本地录音器；开发板采集的批处理回退可以工作，离线测试夹具不能启用产品输入路径。

保留围绕 [语音解析](../../src/agent/internal/agent/speech/text_test.go)、[STT 收尾](../../src/agent/internal/agent/stt_streaming_session_test.go)、[Anthropic 推理重放](../../src/agent/internal/agent/anthropic_thinking_replay_test.go)、[实时准入](../../src/agent/cmd/daemon/realtime_busy_test.go) 和 [开发板播放](../../tests/audio_playback_session_test.cpp) 的现有测试。扩展它们；不要只用正常路径的流测试来替代它们。

为每个已发布的适配器添加脱敏后的提供商协议测试夹具。在夹具元数据中固定模型/API/协议版本，并把不受支持的能力用例纳入测试矩阵。即使某些提供商仍明确只支持批处理，现有提供商也继续受支持。

### 12.2 真实工作流检查

- 开发板：使用开发板麦克风获取一个较长的回复，验证可听见的输出在生成结束之前就开始。反复打断，验证下一轮永远不会播放旧音频。尽可能测量声音/回环，而不只是 socket 时间戳。桌面输出测试使用经批准的开发板录音或隔离的测试夹具，绝不使用桌面麦克风；这些检查要与开发板声学验收区分开。
- 中文、英文以及中英混说：停顿、自我纠正、数字、人名、附和语、噪声和长话语。除延迟外，还要评估 STT 准确率和语音文本的可懂度。
- 至少一个具有显式 ID/取消的现有原生实时提供商，以及事件语义不同的 Gemini；然后对每个已发布的适配器运行一致性测试。覆盖一个原生增量 TTS 和一个缓冲/批处理适配器。
- 测试缓慢/不稳定的网络、冷连接建立、提供商限流、漏掉的语音边界、扬声器播放期间的 AEC，以及长达一小时的会话。
- 在开发板语音处于活跃状态时，测试文本客户端、浏览器观察者、后台任务、通知和设置重载。浏览器实时音频、手机音频和桌面麦克风输入没有验收矩阵，因为它们不在范围内。

## 13. 迁移计划与交付关卡

采用绞杀者（strangler）式迁移：新契约先包装现有实现，然后一次迁移一项职责。不做一次性的大重写，也不做无关的包重命名。参考工期为 **2–3 名工程师、具备开发板硬件和提供商访问权限时 8–12 周**；这是规划范围，而不是承诺。浏览器/广域网语音、手机媒体、桌面麦克风输入和运行时替换被明确排除，而不是另行估算。

| 阶段 | 工作内容与可能涉及的位置 | 退出关卡 |
| --- | --- | --- |
| **0 — 基线与 ADR**（约 1 周） | 采集冷/热启动时间线、实际生效的能力矩阵，以及开发板麦克风/扬声器测量数据；敲定事件标识、所有权、队列和历史策略 | 可复现的基线，以及已批准的范围/SLO 假设；行为不变 |
| **1 — 核心契约**（1–2 周） | 添加叶子流类型、收集器垫片、尝试/epoch 标识、有界队列、终态规则和假时钟测试；桥接当前的运行时 writer 和实时事件 | 契约测试通过；现有调用方和事件格式不变 |
| **2 — 输出纵向切片**（约 2 周） | LLM → 现有语音解析器 → TTS → 呈现协调器；拆分关闭/排空；开发板队列硬上限和停止回执；桌面开发输出端 | 开发板上的长响应在生成结束前即可听到；饱和时取消仍然及时；没有重复的工具语音 |
| **3 — 流式输入**（1–2 周） | STT 转写事件、就绪前缓冲、感知 context 的批处理回退、轮次权威和实时字幕 | 开头的音素得以保留；假设能正确修订；每段话语恰好一个被接受的轮次 |
| **4 — 实时收敛**（约 2 周） | 把守护进程策略提取到接口之后；使用共享的呈现/历史/遥测；保留原生适配器和前台/后台行为 | 提供商重放/取消/看门狗矩阵通过，包括缺失/乱序事件 |
| **5 — 客户端发布与加固**（1–2 周） | v2 事件协商、观察者重新同步、能力 UI、混合版本兼容、浸泡测试和多语言测试；移除已证实无用的垫片 | 经过测量的验收、记录在案的降级模式，并演练过回滚 |

各阶段只有在其契约稳定后才会重叠进行。建议的并行分工：一名工程师负责控制器/运行时，一名负责 STT/TTS/提供商一致性，一名负责 C++ 开发板音频和文本 UI。整个过程都需要硬件/QA 时间。

### 具体的、适合评审规模的工作项

1. 添加流标识/终态测试夹具和能力清单；不改变行为。
2. 围绕现有 LLM 回调添加类型化事件，并加上一个阻塞式收集器。
3. 添加生成/尝试失效以及输出后重试的测试。
4. 提取呈现所有权，并引入 finish/drain/stop 的区分。
5. 修复开发板队列饱和问题，添加丢失/进度协议字段及兼容性测试。
6. 为桌面开发输出端实现实时 PCM；不要添加桌面采集。
7. 桥接现有的语音解析器/TTS 适配器；保留工具和通知的语音行为。
8. 添加 STT 就绪缓冲和感知 context 的批处理取消。
9. 为当前的流式 STT 适配器添加转写修订/定稿/轮次事件。
10. 在保留适配器的同时，把原生实时策略迁移到控制器之后。
11. 添加 Web v2 事件投影、游标/快照恢复，以及实际生效能力的 UI。
12. 添加端到端指标、故障/浸泡测试套件、灰度开关和迁移文档。

现有的 [运行时](../../src/agent/internal/agent/runtime.go#L1156)、[音频对话](../../src/agent/internal/agent/audio_dialog.go#L886)、[实时守护进程循环](../../src/agent/cmd/daemon/realtime_wakeup.go#L1444)、[TTS 契约](../../src/agent/internal/agent/tts/provider.go#L15) 和 [STT 契约](../../src/agent/internal/agent/stt.go#L13) 是主要的切入点。不要一开始就移动数百个文件或全局替换 `langchaingo`。

### 发布与回滚

- 使用一个临时的会话级引擎功能开关；一个会话只使用一个引擎。保留设备级/用户级灰度，以及立即回退到旧版引擎的能力。不要在一段话语中途切换引擎。
- 只用脱敏的测试夹具或录制数据对纯粹的事件合并/投影做影子运行。在没有经批准的实验和用户同意的情况下，绝不重复运行工具、同时播放两个引擎的输出，或把实时音频发送给第二个提供商。
- 先发布服务端/协议兼容性，再让客户端主动启用。在所有受支持的客户端都完成迁移且回滚经过测试之前，保留旧版投影。
- 以明确的 schema 版本存储增量的交付元数据或旁路文件；避免破坏性的历史迁移。验证旧的二进制文件仍能正常运行。
- 在出现过期语音、重复操作、取消延迟回归、持续的内存增长或任务成功率下降时回滚，而不仅仅是在进程崩溃时。
- 只有在测量证明行为一致并经过约定的支持窗口之后才移除兼容代码；不要留下两套永久的编排实现。

## 14. 已确认的范围与待定的决策

### 已确认的产品边界

- 只在现有 Go/C++ 运行时内部构建流式核心。不要用第三方框架替换它，也不要外包语音编排。
- 通过 `audio_service` 的开发板麦克风是唯一的产品语音输入，而不仅仅是首个版本的默认值。没有浏览器、手机或桌面输入。
- 没有浏览器实时语音或手机媒体路径。Web 文本/字幕/事件以及 Phone Bridge 命令/结果保持其现有角色。

### 仍需批准的策略

只有以下剩余的产品权衡需要负责人批准：

| 决策 | 建议的默认值 | 为什么需要确认 |
| --- | --- | --- |
| 必须支持流式的提供商 | 保留所有当前提供商；标记仅输出最终结果的适配器，并提供 `required` 策略 | 对于不受支持的提供商/模型组合，无法承诺真正的流式处理 |
| 默认语音引擎 | 保留当前选择的模式；同时支持级联和原生实时 | 质量、区域、成本、工具控制和语言覆盖各不相同；没有测量出普遍最优的方案 |
| 经典插话 | 默认使用按键打断；AEC 验证后可主动开启全双工 | 误打断和回声取决于真实的硬件/声学条件 |
| 被打断对话的历史 | 保留带状态的生成内容；只重放有交付支持的语音以及打断元数据 | 这是用户可见的行为，并且会改变模型上下文 |
| 延迟 / 成本目标 | 先建立基线；把第 11 节的目标作为初始假设 | 激进的端点检测/推测可能改善延迟，但会损害准确率和成本 |
| 区域验证 | 优先考虑现有的可在中国访问的提供商，外加一条全球参考路径 | 端点区域/代理路由会显著改变感知延迟和隐私约束 |
| 人力与发布 | 2–3 名工程师，8–12 周分阶段的核心迁移，会话级灰度 | 开发板硬件、提供商访问权限和兼容性范围决定排期 |

在剩余策略获批之后，编写简短的契约 ADR 并实施第 0/1 阶段。已确认的范围本身并不授权完成全部实现或合入改动。

## 16. 为本提案完成的工作

- 检查了当前的提供商、运行时、语音、音频服务、客户端、任务和遥测边界，以及它们现有的测试契约。
- 调研了上述官方来源，并把观察到的行为与建议和未经测量的目标区分开。
- 添加了本提案，并在 Agent 概览中添加了指向它的链接。这个初始切片没有改变提供商协议、提示词、配置键、依赖、固件和部署接口。
- 实现了第一个保持兼容性的切片：与提供商无关的 `src/agent/internal/stream` 包现在定义了 v2 事件标识、终态结果、协商得到的音频帧元数据以及感知 context 的有界队列，并配有确定性的单元测试。`AudioPlaybackSession` 现在会在背压等待之后重新检查其硬性队列上限，在饱和持续时返回 `TIMEOUT`，并在停止后拒绝写入。
- 把保持兼容性的实现继续推进到流式输入边界：运行时回调现在会发出类型化的流事件；TTS 会话区分了输入结束、取消、合成完成和播放排空；STT 提供商暴露了感知 context 的批处理调用、有界的就绪前 PCM 缓冲、带修订号的假设、分段定稿、轮次提交以及可选的实时观察者。DashScope 和腾讯的实时适配器现在会发布有界的转写事件通道，而仅支持批处理的提供商仍被明确标识。
- 添加了与提供商无关的转写合并以及有界重放窗口契约。重放窗口能检测过期的 epoch、过期的游标、重复的序号以及需要快照/重新同步的缺口。TTS 能力元数据现在会报告实际的文本粒度和增量音频支持，开发板播放会同时按分块数量和 PCM 时长限制其队列。
- 在 `/api/events?version=2` 添加了一个需主动启用的语义 v2 SSE 路径。运行时流事件会被分配一个进程级的重放游标，通过有界重放广播器交付，慢速观察者会被断开，以便它们重新同步，而不是收到一个未被察觉的不完整流。旧版 SSE 保持不变。
- 添加了一个规范化的实时事件桥接，它把响应、转写、工具、取消、错误和会话生命周期事件映射到共享契约中，过滤过期的输出 epoch，并让 PCM 走独立的音频帧路径。
- 把原生实时守护进程循环接到了语义事件输出端。被接受的提供商生命周期、转写、响应、工具、用量、打断和错误事件现在会到达 v2 观察者路径，并带有过期输出失效机制；PCM 仍由实时播放路径负责。Web UI 消费 v2 流并回退到旧版消息，累积语义文本/推理增量，从重新同步标记中恢复，并使用 `epoch:sequence` 重放 ID 重新连接。
- 为过期的 STT 会话、就绪溢出、转写修订顺序、提供商取消、观察者关闭、重放游标、TTS 能力声明以及播放队列饱和添加了针对性的回归测试覆盖。
- 检查了相对链接/源码行锚点、Markdown 标题片段、代码围栏和空白字符；一次独立的设计评审发现了一个失效的本地标题链接，并已修正。这些只是文档检查，而不是文档构建。
- 针对已实现阶段的 Go 专项测试（包括 `-race`）、Go vet 以及独立的 C++ 播放测试套件均已通过。基于 Docker 的固件测试套件、完整的主机测试套件以及付费的实测/硬件提供商冒烟测试没有运行：当前环境中 Docker 守护进程和部分主机监听功能不可用。凭据已加载，但没有用于付费的提供商调用。
