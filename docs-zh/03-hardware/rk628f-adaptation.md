# RK628F 硬件适配

Aico Link SCH v1 的 J3 同时用于 USB2 ECM 和 Type-C 视频。视频通路为
CSA171 -> CS5366 -> RK628F HDMI RX -> 四条 CSI 通道 -> RV1106。
`RK628_Plugin_DET` 连到 MCU，而不是 RV1106 的 GPIO。因此设备树有意不包含 `plugin-det-gpios` 属性。

旧的 RK628D 驱动无法初始化这颗芯片。开发板在寄存器 `0x0200` 处报告 `0x20230321`，表明它是 RK628F/H。
SDK 现已从 Rockchip 提交 `81417fbf13edb25f203ea794a723b8bf1f457d5c` 向后移植了一整套相互匹配的 RK628 接收器、
时钟/复位、MIPI PHY 和后处理驱动。来源和本地兼容性改动参见
`pico-sdk/sysdrv/source/kernel/drivers/media/i2c/rk628/README.aico`。

开发板保留了板载的 24 MHz 晶振、100 kHz 的 I2C4 M1、GPIO1_A0 电源使能、GPIO1_A1 低电平有效复位、
GPIO1_B1 中断，以及四条连续时钟的 CSI 通道。HPD 由接收器驱动控制，而不是通过启动时把 GPIO 拉高的变通方案。
内置 EDID 与 `edid/hdmi_1080p60_cta.hex` 一致，默认声明 1080p60。frame 服务会专门针对 RK628 应用所选的配置；
通用的 libaico 回退仍为 1080p30，以兼容 TC358743。持久化的 1080p30 兼容配置在保持 1920x1080 采集的同时，
把 HDMI 像素时钟限制在 74.25 MHz。在测试用的 Android 信号源上，板载 Type-C 桥接通路在 148.5 MHz 下反复丢失全部三个数据通道的锁定，
即使在停止采集并保持 HPD 稳定的情况下也是如此。720p60 和 1080p30 在 74.25 MHz 下都能正确锁定。
这是针对所观察通路的兼容性限制；它并不能确定是哪个物理元件导致了较高速率下的不稳定。

## 持久化输入模式

在开发板上使用：

```bash
sudo aico-hdmi-mode 1080p30   # Apply compatibility mode and save it
sudo aico-hdmi-mode 1080p60   # Return to 60 Hz and save it
aico-hdmi-mode status        # Show the configured selection
```

该命令会以原子方式保存 `/userdata/system/hdmi-mode` 并重启 `aico-frame.service`。该选择在重启和 rootfs 槽位切换后依然有效；
没有已保存的选择时，默认为 1080p60。status 报告的是已配置的模式，而不是视频输入已锁定的确认。不存在自动降级。

发现 RK628 接收器之后，frame 服务会在打开采集之前应用该选择，包括桥接芯片在服务启动之后才出现的情况。
它会先比较当前的 EDID，只在配置发生变化时应用一次；常规的采集恢复不会重复这一协商。TC358743 保留其现有策略。
显式配置的 `FRAME_SERVICE_EDID` 会覆盖这一模式策略；使用该模式命令时，请将其保持为 `auto`。

EDID 变更后，Android 信号源可能需要约 30 秒才能完成重新协商。在此期间像素时钟暂时为零，并不能说明新模式不受支持。
评估采集之前，请先观察信号源的显示状态和接收器的锁定状态。

用户空间的 EDID 更新会停止推流、将 HPD 保持为低电平，并重新调度接收器配置。没有输入时返回 `ENOLCK`，
而不是成功地回退到 VGA 时序。由于没有插入检测 GPIO，训练失败后会以十秒的延迟自动重试。

## 接收器恢复

系统恢复时，必须在接收器初始化和时序获取之前，把 CPLL 恢复到探测时所用的同一个 1194 MHz 参考频率。
掉电之后经过通用的 CRU 初始化，它会停留在 1188 MHz，而 HDMI 时序计算假定的是 1194 MHz。在测试的开发板上，
这导致 1080p60 输入被报告为接近 149.25 MHz 而非 148.5 MHz，并在原始帧中产生持续的斜向画面损坏。
时钟和所有 HDMI 通道都保持锁定；重启采集或重写相同的 EDID 都无法修复。RK628 内部彩条是完好的，
恢复经过校准的 CPLL 频率后，手机画面在 1080p60 下恢复正常。PLL 锁定轮询最多读取 100 次，每次之间休眠 1 ms。
超时返回 `ETIMEDOUT`；I2C 读取失败则保留其原始 errno。探测和恢复在 CPLL 失败时中止。
恢复失败时会重新关闭接收器电源，并保持 IRQ 和热插拔任务禁用，而不是在参考时钟未锁定的情况下继续。
音频父 PLL 的错误也会向上传递，而不会根据无效的频率设置分频器。

接收器配置只采样一次字符错误，并把该结果同时用于就绪判断和重试决策。读取计数器可能会更新其基线和均衡器，
因此第二次读取可能显示为无错误，从而错误地抑制了必要的重试。启用字符错误监控时，采样其计数器可能会根据长时间空闲期间累积的错误
重新调整均衡器，从而扰乱已锁定的输入。因此开始推流时不会触碰这些计数器；均衡器的调整只在接收器训练中进行。
开发板设备树禁用了字符错误监控和动态 EQ，因为启用动态 EQ 的试验未能实现可靠的采集。仅凭字符错误计数器无法判定线缆故障。

即使 HDMI 时钟、全部三个数据通道和解码后的输入模式都保持稳定，RK628F 在其测量结果趋于稳定的过程中也可能触发垂直有效行中断。
驱动会对这些中断进行 100 ms 的去抖，并将输入与上次配置的时序和色彩元数据进行比较。通道锁定检查会在 80 ms 内重试，
因此短暂的锁定状态下降不会重置一个实际未变化的输入；持续的锁定丢失仍会触发重新训练。
对于未变化的输入（允许 0.1% 的像素时钟测量偏差），当前推流会继续运行。链路丢失或真实的模式/色彩变化仍会停止推流并重新训练接收器。
在去抖期间，时序查询无法替换已配置的比较基线。

在接收器丢失数据通道锁定、且测得的有效行少于 1080 行时，AVI 数据包仍可能继续声明 1080p60。因此仅靠标准模式查找无法确定视频是否稳定。
时序获取所用的每个样本都会在读取时序之前和之后检查时钟以及全部三个数据通道的锁定状态。锁定丢失会打断连续八个稳定样本的序列，
返回 `ENOLCK` 并清除输出时序；寄存器读取错误保留其原始 errno。这可以防止过时的 AVI 元数据发布输入就绪状态。
它并不能修复不稳定的 HDMI 链路，也不能保证后续帧的送达。

在恢复和叶子掩码更新期间，父级 HDMI 中断保持屏蔽。这可以防止在恢复工作线程持有配置互斥锁时，挂起的中断独占 I2C。
CSI 中断路由保持不变。一个共享的互斥锁将线程化的 HDMI 处理程序与掩码更新串行化。
配置忙时 `VIDIOC_QUERY_DV_TIMINGS` 返回 `EAGAIN`，没有信号时返回 `ENOLCK`。

每次成功的常规时序查询都会选择单路或双路 MIPI 模式。1080p60（148.5 MHz）和 1080p30（74.25 MHz）都使用单路 MIPI 模式。
这些选择消息在驱动调试级别 1 下可见；仅仅是它们重复出现，并不表示接收器在恢复或采集失败。

推流启动/停止和格式就绪检查共享接收器配置互斥锁，因此恢复流程不会在推流切换进行到一半时重置 CSI。
输入不可用时 `STREAMON` 返回 `ENOLCK`，推流设置本身触发恢复时返回 `EAGAIN`。启动失败时会在返回错误之前禁用 CSI，
使采集服务可以重新打开信号源。CSI PHY 锁定和通道 stop-state 轮询失败时，会通过 `STREAMON` 返回其原始错误，
例如 `ETIMEDOUT` 或 I2C 错误。设置失败时会让发送端和 PHY 都保持禁用，而不是报告一个正常工作的推流。

在受影响的镜像上，frame 服务可能一直停留在 `RECOVERING`，且 `latest_seq=0`、`frame_age_ms=0`、
`last_error=open failed`。这里帧龄为零表示不存在任何帧时间戳。请检查 `/var/log/frame_service/frame_service.log`
和 RK628 内核日志中是否有反复的接收器复位。仅凭显示器枚举无法证明采集正常工作。

CIF 启动可能在启用其帧完成 tasklet 之前就失败，例如接收器格式就绪检查返回 `EAGAIN` 或 `ENOLCK` 时。
失败清理只有在本次启动尝试确实启用了该 tasklet 时才能禁用它。否则每次早期失败都会增加禁用计数，
之后成功的 `STREAMON` 调用会让帧完成保持禁用。此时挂起的 tasklet 会反复唤醒 `ksoftirqd`，采集出队超时，
重新打开摄像头也无法消除这种不平衡。启动路径会记录它是否启用了 tasklet，然后在清理时对该操作进行配平。
部署修正后的 CIF 模块需要重启，才能清除已经受影响的实例。这解决的是接收器瞬时失败后采集持续停滞的问题；
接收器锁定丢失仍需要单独评估。

## 硬件验证

在所连接的主机处于唤醒状态时，检查以下所有项：

1. 内核日志报告 `RK628F/H (20230321)`。
2. 主机默认枚举出 1920x1080、60 Hz 的 `Linux FHD60`，或在选择兼容模式后枚举出 30 Hz 的 `Linux FHD30`。
3. `v4l2-ctl -d /dev/v4l-subdev2 --query-dv-timings` 返回已锁定的非零输入时序。如果编号发生变化，
   请使用 `media-ctl -p` 找到实际的子设备。
4. `/sys/kernel/debug/rk628/4-0050/hdmirx/status` 显示时钟和全部三个 HDMI 数据通道均已锁定。
5. `frame_service_cli --socket /run/frame_service/frame_service.sock
   screenshot --out /tmp/capture.jpg` 返回一张真实图像，并且当主机画面变化时，连续采集的结果也随之变化。
6. 软件重启后重复上述检查，并验证 Wi-Fi 恢复以及 `systemctl --failed`。

仅凭主机显示器枚举只能验证 HPD/DDC，而不能验证像素传输。处于睡眠状态的主机可能保持显示器已枚举，却不发送任何视频时钟。
在这种情况下，驱动必须报告无信号。

SDK BSP 的构建和审计会编译该硬件驱动。Docker 测试套件 `bash scripts/run_tests_in_docker.sh --suite rk628-recovery`
会使用模拟寄存器运行生产环境的恢复函数，在反复的早期和晚期失败之后测试 CIF 启动，并检查开发板/EDID 的集成约定。
修改后请运行必需的本地 `make check` 配置；CI 会运行 `make check-full`。
